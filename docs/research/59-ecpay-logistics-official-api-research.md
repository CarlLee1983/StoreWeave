# ECPay Logistics API — official-source adapter research

**Accessed:** 2026-08-24. **Scope:** domestic logistics only; official ECPay web properties and the `ECPay` GitHub organisation. No credentials were used and no API request was made.

## Verified findings

1. ECPay publishes two different domestic-logistics integration contracts, which must not be mixed: **物流整合** is a one-step, server-to-server/form-data flow with MD5; **全方位物流服務** adds temporary orders and ECPay's responsive logistics-selection page, and uses JSON plus AES. ECPay's 2021 announcement says both remain available. [Developer portal](https://developers.ecpay.com.tw/#logistics), [announcement](https://www.ecpay.com.tw/announcement/DetailAnnouncement?nID=4428) (accessed 2026-08-24).
2. ECPay's official PHP SDK says it supports all-in-one logistics, domestic logistics, and cross-border logistics; it directs users to examples and the integration documents. This is evidence that an SDK exists, not a guarantee of API parity or a reason to couple this adapter to PHP. [SDK_PHP](https://github.com/ECPay/SDK_PHP) (accessed 2026-08-24).
3. For the newer all-in-one API, selected documented endpoints are verifiable: `POST` JSON `https://logistics-stage.ecpay.com.tw/Express/v2/QueryLogisticsTradeInfo` / production equivalent for order lookup; `POST` JSON `.../PrintTradeDocument` for a document after order creation; and `POST` JSON `.../CreateByTempTrade` to promote a temporary order. Exact creation/update/return fields are intentionally not reproduced here; they vary by logistics subtype and must be taken from the relevant official operation page at implementation time. [query](https://developers.ecpay.com.tw/10171/), [print](https://developers.ecpay.com.tw/10107/), [create from temporary order](https://developers.ecpay.com.tw/10118/) (accessed 2026-08-24).
4. The newer API's outer request/response concept is confirmed: merchant identifier, timestamp header, and encrypted `Data`; ECPay describes `Data` as encrypted JSON. `TransCode=1` means the transport data was received, while business success is represented by decrypted `RtnCode` (`1` success). Timestamp validation is stated as five minutes, so host clock synchronisation is an operational requirement. [query contract](https://developers.ecpay.com.tw/10171/), [status notification contract](https://developers.ecpay.com.tw/10127/) (accessed 2026-08-24).
5. The newer API encryption is confirmed as URL-encode data, then AES-128-CBC with PKCS7 padding using ECPay-provided key and IV. Test and production keys must be different. This establishes secret handling and protocol direction; do not infer cipher implementation quirks beyond the official example when coding. [encryption appendix](https://developers.ecpay.com.tw/10205/) (accessed 2026-08-24).
6. Merchant trade numbers are documented as unique/non-reusable for both lookup and converting a temporary order to a formal order. This is the only explicit idempotency-like guarantee located; it supports persisting a locally generated, stable merchant trade number and reconciling before retrying an ambiguous create, but **does not prove that create is idempotent**. [query](https://developers.ecpay.com.tw/10171/), [create from temporary order](https://developers.ecpay.com.tw/10118/) (accessed 2026-08-24).
7. Status updates are server POST callbacks to the configured `ServerReplyURL`; ECPay says the merchant must reply `RtnCode=1`. Missing/incorrect acknowledgement is retried every 60 minutes, up to three times that day; notifications are not real time and may fail to advance. Callback processing must therefore be authenticated/decrypted per the documented envelope, durable, duplicate-tolerant, and supplemented by query reconciliation. [status notification](https://developers.ecpay.com.tw/10127/) (accessed 2026-08-24).
8. ECPay documents operational gates beyond credentials: production merchant IDs, endpoint environment, and approved logistics subtype must match; a logistics service must be enabled. For B2C 7-ELEVEN/FamilyMart bulk shipping, test-label approval is required before shipping; low ECPay account balance prevents logistics-order creation. [FAQ](https://developers.ecpay.com.tw/62276/), [formal-order prerequisites](https://developers.ecpay.com.tw/10118/) (accessed 2026-08-24).
9. Label/document generation is not a normal JSON artifact download: the all-in-one print operation is documented as an API that produces a print flow, and ECPay's FAQ warns that server-side receipt/Postman handling can leave the user at an intermediate page; it says client-side POST should handle the redirect to the print page. Treat label retrieval as a browser/print workflow until a provider-approved downloadable artifact is demonstrated. [print operation](https://developers.ecpay.com.tw/10107/), [FAQ](https://developers.ecpay.com.tw/62276/) (accessed 2026-08-24).

## Repo implementation boundary / external gates

- The adapter may model a provider credential set (merchant ID, key, IV), test/production base URL selection, encrypted request envelope, order identifier mapping, query, and an inbound callback handler. Store keys outside source control; never log plaintext encrypted payloads or personally identifiable shipping data.
- Keep formal order creation behind a durable outbox/job and a per-order provider-operation record. On timeout/unknown result, query by the persisted merchant trade number or provider logistics ID before any retry. This is a conservative **inference** from the uniqueness rule and non-idempotent operations; official documentation does not advertise an idempotency key or retry contract.
- Do not claim automatic label download, tracking timeline completeness, cancellation/return support, carrier availability, or a public callback-domain allowlist. These require the selected ECPay contract, logistics subtype, merchant account configuration, and production verification.
- External prerequisites: a merchant ECPay account with the intended logistics services activated, corresponding production credentials, adequate prepaid balance where applicable, clock synchronisation, a reachable HTTPS callback endpoint, and any required B2C test-label approval. The precise callback-domain registration/validation rules were **not found** in the public official pages reviewed.

## Explicit unresolved gaps

- Which contract StoreWeave should support first (legacy form-data/MD5 versus all-in-one JSON/AES), and which carriers/subtypes the merchant has actually enabled.
- Exact create/update/cancel/return field matrices, error-code mapping, rate limits, retry semantics, and callback authenticity/response details beyond the public envelope; obtain these from the exact official operation pages and sandbox validation after account provisioning.
- Whether print output can be captured as a file without browser interaction; the official FAQ points the other direction.
- Production callback reachability/domain onboarding, label-layout requirements, and tracking-status normalization need merchant-account confirmation and controlled sandbox/production acceptance testing.
