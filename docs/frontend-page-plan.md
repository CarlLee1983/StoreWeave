# 顧客前台頁面規劃

**狀態：** 目前可由既有 Theme DTO 支援的前台頁面已完成：共用 Theme shell、同源字型交付、首頁／商品詳情、購物車、既有建立訂單確認、登入／帳戶與訂單紀錄。本文件不新增 API 契約；付款與物流 UI 留待後端契約完成後再開啟。

**設計基準：** [Default Theme 顧客前台設計規格](../packages/themes/default/DESIGN.md) 是字型、色彩、資料邊界與可下單行為的單一設計來源；本文件負責頁面範圍與 worktree 順序。

**範圍：** 顧客面向的 Storefront SSR Theme；營運後台 `apps/admin` 不在本輪製作範圍。

## 工作契約

後台已有明確的操作型設計基調；本輪要補的是顧客前台的資訊架構與視覺基礎，而不是重做 Admin。

- 將既有、功能完整但視覺極簡的 Default Theme 整理成一致的購物體驗。
- 保留 SSR 與標準表單 POST；有 session 時保留 CSRF hidden field，匿名 guest cart 則沿用既有同源寫入檢查。沒有 JavaScript 也必須能瀏覽、加車與結帳。
- 不假設尚未提供的商品資料，例如商品圖片、分類、評價或運費承諾；這些需要先有對應 DTO／契約。
- 不把 Admin 元件或樣式搬到前台。可借鑑其「清楚、克制、可讀」的品質，視覺語言則以顧客選購為中心。

驗收條件：後續實作者能從本文件判斷每個前台頁面的使用者任務、主要狀態、共用元件、行動版要求與 worktree 邊界；主工作目錄維持不受影響。

## 體驗方向

前台應傳達「可信、好找、容易下單」，而非後台的高資訊密度操作台。

- **商品優先：** 商品名稱、價格、可售狀態與主要行動在首屏可辨識；沒有圖片資料時，不假裝有圖片導向的版型。
- **低摩擦：** 購物車、折扣、購物金與結帳的每一步都能說明目前金額為何改變。
- **可信賴：** 付款處理、庫存不足、優惠無效與訂單狀態使用清楚文字，不以樂觀更新掩蓋伺服器最終結果。
- **可近用與行動優先：** 以單欄手機版為基準，桌面再擴為兩欄的內容／摘要版型；所有表單欄位都有可見 label 與可理解的錯誤訊息。

設計基礎應由 Theme options 驅動：品牌色沿用既有 `accentColor`，另建立前台專用的 surface、文字、邊框、成功／警示／錯誤 token。字級、間距、按鈕與卡片半徑只保留一套；不可直接複製 Admin 的 sidebar、資料表密度或深色預設。

## 示範品牌假設

本輪以前台原創品牌 **「織日選物／Woven Day」** 為設計基礎：一家販售居家織品、桌面小物與日常器物的線上選物店。它和 StoreWeave 的平台名稱有輕微呼應，但不是既有品牌，也不借用第三方識別。

| 面向 | 假設 |
| --- | --- |
| 目標客群 | 25–40 歲、偏好有質感但不疏離的日常用品的城市消費者 |
| 語氣 | 溫暖、簡潔、具體；不使用浮誇促銷語或假造品牌故事 |
| 視覺 | 淺燕麥色背景、墨棕文字、陶土橘作主要行動色、苔綠作低調狀態色；高對比文字維持可讀性 |
| 字體 | 採 Google Fonts 的 Noto Sans TC 與 Noto Serif TC；原型可直接用 Google CSS API 預覽，正式 Theme 自託管 WOFF2，不能在帶有 session 的頁面依賴第三方字型 CDN |
| 商品呈現 | 在沒有商品圖片契約前，以名稱、價格、可選描述與 SKU 資訊建立層次；不以 AI 圖或網路圖片冒充真實商品 |

這是原創的設計方向，而不是對任何商店的複刻。若日後使用外部參考，僅取其抽象的體驗原則，例如「清楚的商品層級」或「結帳步驟易懂」，不複製其素材、文案、版型或識別元素。

## 字型與可下單的設計界線

字型、token 與元件詳細規則已收斂至 Default Theme 顧客前台設計規格。原型使用 Google Fonts 來確認設計選擇；正式實作則將已選定字型隨應用程式靜態資產發布。現有 SSR layout 已禁止第三方可執行 script；本規格再要求字型不使用第三方 CDN。

「可以下單」在這裡不是新增一組前端 mock，而是讓每個畫面保留 Platform 的既有介面：

- 商品列表只顯示 ThemeProductView 目前提供的 id、sku、名稱、描述、價格、幣別與可售數量；available 是數量或 null，只有零或負數代表售完。媒體、分類、變體、評價與運費等資料必須先擴充 DTO。
- 商品詳情以 GET /p/:id 進入，加入購物車以 POST /cart/items 送出 productId 與 quantity；只有 Context 提供 token 的 session 請求才輸出 hidden CSRF field，訪客 guest cart 沿用同源寫入檢查。
- 購物車中的金額與可售性由 server 重算，購物車不保留庫存；任何價格或庫存落差都必須顯示 server notice。
- GET /checkout 會要求 customer 登入；提交要保留 cartId、CSRF 與伺服器端冪等行為，成功後以訂單資料顯示付款狀態。

因此首頁原型的商品圖片、分類、搜尋和加入動作不得直接搬入正式 Theme。選定版型後，先以真正的 Theme renderer、資料介面與標準 POST 表單重新實作。

## 頁面資訊架構

```text
商品瀏覽
首頁／商品列表 → 商品詳情 → 購物車 → 結帳確認 → 訂單詳情
                                  ↑
                  登入／註冊 ────┘

會員服務
帳戶導覽 → 我的訂單／我的券／購物金與等級／個人資料
```

| 頁面 | 使用者要完成的事 | 核心內容與狀態 | 行動版重點 |
| --- | --- | --- | --- |
| 商品列表 `/` | 找到可購買商品 | 商品卡、價格、可售數量／售完、空清單 | 單欄卡片；固定且不遮擋內容的帳戶／購物車入口 |
| 商品詳情 `/p/:id` | 了解商品並加入購物車 | 名稱、SKU（依 Theme option）、價格、描述、數量、可售數量／售完、加入結果 | 主要 CTA 在價格與數量後立即可見；售完時不可提交 |
| 購物車 `/cart` | 調整購買內容與得知即時試算 | 商品列、數量／移除、商品小計、調整明細、門檻提示、折扣碼、購物金、空車與失效商品提示 | 每筆商品以卡片呈現；金額摘要與前往結帳 CTA 保持明確 |
| 結帳確認 `/checkout` | 核對不可變更的內容並提交 | 訂單列、最終預估、通知 email、伺服器錯誤、送出按鈕 | 單一主要動作；回購物車是次要連結，避免兩個同權重 CTA |
| 訂單詳情 `/orders/:number` | 查詢訂單／付款最新狀態 | 訂單編號、狀態、付款處理／逾時說明、品項、總額 | 訂單狀態在標題後立即呈現；表格在小螢幕改為語意清楚的堆疊內容 |
| 登入、註冊、重設密碼 | 取得或恢復帳戶 | 單一表單、欄位錯誤、下一步連結、成功提示 | 不與商品選購畫面混排；維持最短可完成表單 |
| 我的訂單 | 回看自己的訂單 | 只顯示自己訂單、件數、金額、日期、分頁與空狀態 | 訂單摘要卡取代橫向捲動表格 |
| 我的券 | 找出可用優惠 | 代碼、優惠說明、到期日、可用／不可用理由、即將到期 | 可用與即將到期的視覺優先順序清楚；不可用原因保持可讀 |
| 購物金與等級 | 理解可用金額與等級進度 | 可用／待生效／近期到期、帳本、等級、升級進度、計算方式 | 餘額與到期日先行；帳本列改為可掃讀的記錄卡 |
| 個人資料 | 管理可用於後續下單的資料 | 顯示名稱、電話、生日限制、地址、儲存結果／錯誤 | 地址欄位單欄排列，生日不可修改的限制在欄位旁說明 |

## 共用組件與狀態

先建立下列 Theme 層級元件／樣式規則，再逐頁套用，避免每個頁面各自寫一套按鈕、提示與版距。

| 類別 | 前台專用組件／規則 |
| --- | --- |
| 全站殼 | 品牌、帳戶導覽、購物車入口、主內容最大寬度、footer；登入與未登入狀態都要可判讀 |
| 導覽 | 商品瀏覽、帳戶區與回上一層的連結；不可依賴 JavaScript 控制導覽狀態 |
| 商品與價格 | 商品卡、價格呈現、可售狀態、數量輸入、主／次要 CTA |
| 結帳摘要 | 商品小計、調整、折扣、購物金、總額的固定順序與負數金額格式 |
| 回饋 | notice、error、success、status badge、空狀態；文字必須說明原因與可採取的下一步 |
| 帳戶內容 | 頁首、帳戶次導覽、記錄列表／小螢幕卡片、分頁 |

商品媒體、搜尋、分類篩選、收藏、推薦與多地址簿不在本輪元件清單中：目前沒有足以支撐它們的產品資料或使用者任務，不能用假資料把它們做成永久 UI。

## 實作順序與 worktree 邊界

目前 `packages/themes/default/src/index.ts` 集中大多數頁面 render function；若直接讓多個 worktree 同時改它，衝突會很高。本次已在 `codex/frontend-page-plan` 單一 worktree 串行完成 foundation、商品瀏覽、購買呈現與帳戶呈現；未來的付款／物流契約應另開 worktree，避免重疊修改同一個 renderer。

1. **已完成：前台基礎 + 商品瀏覽 worktree（串行）**：建立前台 token 與共用 layout／元件邊界、同源字型資產，並完成商品列表與商品詳情；保留 `defaultTheme` 公開契約與現有 HTML 表單 action。
2. **已完成：購買呈現**：完成購物車與建立訂單確認的內容／摘要版面、折扣／購物金、空車、失效商品、錯誤與現有提交動作。
3. **已完成：帳戶呈現**：完成登入／重設、訂單、優惠券、購物金與個人資料的共同帳戶層級與響應式記錄列表。
4. **下一個 worktree：付款／物流契約**：先擴充 DTO、Controller、付款 provider／webhook 與配送資料，再做正式結帳步驟、付款結果與追蹤 UI。
5. **整合驗收（串行）**：重新檢查所有 Theme contract、SSR 表單、響應式版型與既有 integration tests。

| 分支建議 | 擁有範圍 | 前置條件 |
| --- | --- | --- |
| `codex/storefront-foundation-*` | `layout.ts`、renderer 模組拆分、前台 token／共用樣式、`index.ts` 組裝 | 單一 writer；先整合 |
| `codex/storefront-catalog-*` | 商品列表／詳情 renderer 與對應樣式、測試 | foundation 已整合 |
| `codex/storefront-purchase-*` | 購物車／結帳 renderer 與對應樣式、測試 | foundation 已整合 |
| `codex/storefront-account-*` | Auth／帳戶／訂單 renderer 與對應樣式、測試 | foundation 已整合 |

後台檔案（`apps/admin/**`）不屬於任何上述 worktree。若前台需求缺少資料，另開後端契約 worktree，先確認 Theme DTO 與 Controller 行為，再回到該頁面切片。

## 驗證基線

- Theme 變動先跑受影響的既有 integration tests，例如 cart、coupon、rewards、account orders、auth 與 password reset。
- 每個切片完成後跑 `pnpm test`；若只改 Theme 呈現且已有更窄測試入口，先跑窄測試再跑全套。
- 變動組裝或靜態資源後跑 `pnpm build`。
- 以實際瀏覽器檢查至少 360px 與桌面寬度；檢查鍵盤操作、可見 focus、表單錯誤和不載入 JavaScript 的交易流程。

## 已可使用的範圍與下一步

目前可由既有資料支撐的顧客頁面已完成。若日後要替換成真實品牌，只需替換 Theme options、設計 token、Logo 與商品內容；既有頁面責任、交易流程與 SSR 契約不需要重寫。正式付款、配送與物流追蹤則必須先完成後端契約，不能由 Theme 先行猜測欄位或流程。
