# 0034. 編輯照片仍由 Theme 擁有，Core 只存一個封閉的圖片 key

- 狀態：accepted
- 日期：2026-08-26
- 修訂：ADR 0026

## 背景

ADR 0026 為了改用 Google Fonts CDN，把整套 Theme 靜態資產機制刪掉，理由是「它只為了送字型
而存在，改走 CDN 之後沒有其他使用者」。那個判斷在當時是對的。

三天後 `f578662` 為了織日選物的編輯照片，把 `resolveThemeAssetsDir`、`/storefront-assets/`
掛載與 build／release 的複製步驟加了回來——不是為了字型，而是為了七張隨 Theme 發布的照片。
0026 的 `Falsified if` 指名的是「`StorefrontTheme` 重新出現靜態資產宣告」，新的機制改走
release 目錄約定、沒有回到那個介面上，因此那句話沒有字面觸發，但它要守的東西已經不成立了：
Storefront 現在有同源靜態資產。這是那條件寫得太窄，不是機制偷渡。

ADR 0033 把品牌內容搬進 Core 之後，問題變成：文章的配圖跟著進 Core 嗎？

## 決策

**照片的位元組仍然屬於 Theme，Core 只存一個 key。** `content_article.image_key` 存
`woven-day-journal` 這種不含副檔名與路徑的識別字，由 Theme 匯出的封閉清單決定哪些 key 合法；
`/storefront-assets/` 繼續存在，繼續只服務那份檔名封閉的清單。

理由是專案目前**完全沒有上傳能力**——沒有 multipart、沒有物件儲存、沒有簽章網址、沒有尺寸
與型別的把關，release 打包也不知道要帶哪些使用者檔案。為了讓一則公告能配圖而長出這一整套，
是拿一個完整的子專案換一個欄位。依「最簡實作、抽象等具體需求到了再加」的規則，這輪不做。

**同時修訂 ADR 0026。** 0026 中「移除整套 Theme 靜態資產機制」的部分作廢；字型走 CDN 的決定
與它的隱私取捨不變。同源靜態資產這條路線由這篇接手，判準也換了：它不再是為了送 5.42 MB 的
字型，而是為了送幾張有限、具名、隨版本發布的編輯照片——這兩件事的流量與維護成本不在同一個
量級，0026 用來否決自託管的理由對它並不適用。

## 後果

- 店家在 Admin 新增一則最新消息時，配圖只能從既有清單挑，不能上傳新圖。這是這個決定最直接的
  代價，也是它最可能被推翻的地方。
- Admin 的圖片欄位是下拉選單而不是上傳元件；清單由 `GET /api/v1/content/articles/image-keys`
  從 Theme 匯出的 `editorialImageKeys` 提供。key 是 Theme 的語意名稱（`hero`、`journal-room`），
  不是檔名——檔名只存在於 Theme 內部，任何外部輸入都不會變成路徑。
- Core 存的 key 可能指向一張 Theme 已經拿掉的圖。Storefront 對不存在的 key 以無圖版型呈現，
  不讓一張缺圖變成整頁失敗。
- 離線／內網部署照常有圖；ADR 0026 提到的「release 不再包含 Theme 靜態資產」不再成立。
- 真的需要店家自行上傳時，這篇會被一篇談媒體儲存的 ADR 取代，屆時 `image_key` 要換成指向
  媒體資料表的參照——那是一次有 migration 的改動，不是加個欄位。

## 考慮過的選項

- **這輪一併做媒體上傳。** 否決：它自帶儲存後端、尺寸與型別把關、備份、release 打包與一組
  安全面向的連帶改動，規模與 content 模組本身相當。要做應該是它自己的一輪。
- **文章一律不配圖。** 否決：生活誌的版型是照片帶動的，拿掉圖等於把上一輪剛做完的呈現退回去。
- **把照片以 base64 存進資料庫欄位。** 否決：它把「沒有物件儲存」這個事實藏進資料列，
  代價是每次查文章都拖著幾 MB，而且仍然沒有解決把關與尺寸的問題。

## Falsified if

`apps/api/src/theme-assets.ts` 的 `resolveThemeAssetsDir` 被移除，或
`packages/commerce/content/src/schema.ts` 的 `imageKey` 不再是字串 key 而改為指向某張媒體
資料表的參照，或專案出現任何接受 multipart 上傳的端點。

前者代表同源靜態資產又被判定為不需要（回到 0026 的立場），後兩者代表媒體所有權已經移進
Core——任一成立，這篇連同它對 0026 的修訂都要重新檢視。
