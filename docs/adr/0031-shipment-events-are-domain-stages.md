# 0031. 出貨事件只表達領域階段，不轉述廠商狀態碼

- 狀態：accepted
- 日期：2026-08-24

## 背景

綠界物流會把狀態變化 POST 回 `ServerReplyURL`，帶一個 `RtnCode`。那組狀態碼數量遠多於
「送出去了、到店了、取走了」——而且**各家超商不一樣**，7-11、全家、萊爾富、OK
各有各的碼與各自的中間態。

事件是這套系統的公開契約：`<context>.<aggregate>.<action>.vN`（ADR 0006），
會被 `demo-erp` 這類 extension 訂閱，也會被未來的外部整合讀到。

## 決策

出貨只發五支事件，全部是領域階段：

- `commerce.order.paymentInfoIssued.v1` —— 取號完成，帶繳費資訊與期限
- `commerce.shipment.created.v1` —— 物流單已建立
- `commerce.shipment.shipped.v1` —— 已出貨
- `commerce.shipment.arrived.v1` —— 已到店待取（只有超商取貨有）
- `commerce.shipment.completed.v1` —— 已取貨或已簽收

廠商的原始狀態碼留在 `shipping_shipments` 的欄位與稽核紀錄裡。要看得用查詢，
不從事件拿。退回目前不發事件。

## 考慮過的選項

- **把 `RtnCode` 原封不動放進事件 payload。** 否決：那等於要求每一個訂閱者去理解綠界，
  而換物流商時所有訂閱者一起壞掉——事件契約的版本號保護不了語意的改變。
  真正的問題是它把「我們用哪一家」洩漏進公開契約。
- **事件細分到跟廠商狀態碼一樣的粒度。** 否決：各家超商的碼不一樣，
  細分等於把事件契約綁在「目前接了哪幾家超商」上，加一家就要加事件。
- **完全不發物流事件，訂閱者自己輪詢查詢。** 否決：ERP 需要知道何時可以出帳、
  何時該通知顧客，那正是事件存在的理由。

## 後果

- ERP 拿不到原始狀態碼。如果那是真需求，它應該是一支 query 而不是事件——
  查詢可以隨廠商改變，事件不行。
- 五個階段不足以表達「配送異常」「退回中」這類情況。目前的處理是：
  訂單取消不同步取消物流單（那個外部呼叫可能失敗、包裹可能已經出庫），
  改由後台的「物流待處理」清單揭露。**「訂單已取消但包裹還在路上」是一個真實存在的
  中間狀態**，把它顯示出來比假裝它不存在好。
- `arrived` 只有超商取貨會發，宅配不發。訂閱者不能假設五支事件都會依序出現。

## Falsified if

`packages/commerce/shipping/src/events.ts` 的任一事件 payload 出現物流商的原始狀態碼
或以廠商命名的欄位，或事件數量開始隨著新接的超商通路增加。

任一成立，代表事件契約已經跟著廠商走，這篇記的理由要重新檢視。
