# 0019. 購物金與等級積分是分批帳本，餘額與等級是推導值

- 狀態：accepted
- 日期：2026-08-22

## 背景

Spec 0005 要的兩件事表面上都可以用一個欄位表達：顧客有多少購物金、他是哪一級。
最省事的做法是在 `customer_customers` 上加 `reward_balance_cents` 與 `tier_name`，
每次入帳、折抵、取消就加減那個欄位。

但購物金能折抵訂單金額——它是一本負債帳。而餘額欄位有三個具體的失敗方式：
併發的兩筆折抵各讀到同一個舊值；某條路徑忘了回沖；某次手動修資料把它改壞。
三者都會讓「帳對不起來」，而且**事後無法重建**：沒有分錄，就沒有真相可以比對。

等級的問題不同但同源：滾動十二個月的積分會自己過期，欄位不會自己變小。

## 決策

兩者都以 **append-only 的分批帳本**記錄，餘額與等級都是帳本的推導值：

- `loyalty_reward_entries`：正數是入帳、負數是折抵或回沖。每一批有自己的生效日與
  到期日。可用餘額由 `deriveRewardBalance()` 推導，**扣抵先用先到期的那一批**。
- `loyalty_tier_entries`：等級積分。等級由 `deriveTier()` 以滾動十二個月的總和推導。
- 回沖一律是**新的反向分錄**，不是把原本那一列改掉。
- `loyalty_customer_tiers` 存目前的等級，但它是**快取**：定價的熱路徑不必每次重算
  整本帳，真相仍然是 `deriveTier(帳本)`。

這個結構從第一天就採用。從餘額欄位改成帳本是資料遷移地獄——舊資料沒有分錄可以重建；
反過來（帳本加一個快取欄位）很容易。

## 考慮過的選項

- **餘額欄位 + 一張流水表。** 否決：兩份真相遲早會分歧，而分歧時沒有規則決定誰對。
  快取欄位與它不同：快取可以隨時從帳本重算，餘額欄位不行。
- **不分批，只記金額與到期日。** 否決：「先到期的先用」需要知道每一筆用掉了誰。
  不分批就只能用「整體到期日」，而那對顧客不利也讓到期通知失去意義。
- **每次折抵時就把批次標記成已用完。** 否決：那就是在改既有分錄，回沖時要反向改回去，
  等於把帳本退化成餘額欄位的複雜版本。

## 後果

- **每次讀餘額都要讀完那位顧客的整本帳。** 目前每人的分錄數是「訂單數 × 2」等級，
  可以接受；真的變大時的解法是加一列「結算到某個時點的快照」分錄，而不是改回欄位。
- 「先到期的先用」讓餘額計算不能是簡單加總——這是選擇分批帳本的主要成本，
  也是它唯一的複雜之處。
- 扣抵分配在**帳本順序**上進行，因此同一時刻的入帳與扣抵必須先算入帳，
  否則一筆本來抵銷得掉的扣抵會落空。
- 有一條守門員測試：一連串入帳、折抵、取消、到期之後，
  「帳本總和 = 可用 + 未生效 + 已過期」仍然成立。

## Falsified if

`packages/commerce/loyalty/src/balance.ts` 的 `deriveRewardBalance` 或
`packages/commerce/loyalty/src/tier.ts` 的 `deriveTier` 不再是純函式、
或 `packages/commerce/loyalty/src/schema.ts` 出現一個被就地加減的餘額欄位、
或 `packages/commerce/loyalty/src/service.ts` 的回沖改成 update 既有分錄
—— 任一項成立，代表「餘額是推導值」這個決策已經被換掉，這篇記的理由要重新檢視。
