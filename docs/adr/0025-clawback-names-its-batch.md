# 0025. 扣回指名批次，是「先到期先用」的唯一例外

- 狀態：accepted
- 日期：2026-08-23

## 背景

ADR 0019 決定購物金是分批帳本，餘額是推導值，而**扣抵先用先到期的那一批**。
那條規則對折抵是對的：顧客花的應該是手上最快過期的錢，否則那批會白白過期。

但帳本裡的負分錄不只有折抵。取消訂單時要把那張單累積的購物金扣回來，
而扣回問的是完全不同的問題——不是「該花哪一批」，是「**收回哪一批**」。
把它交給先到期先用，扣掉的就會是當下最快過期的那一批，而那通常不是那張單累積的那一批。

具體的壞法（工單 54）：顧客有一批客服補償的 300 元下週到期，又下了一張單累積 100 元
一年後到期。那張單取消，扣回的 100 元從補償那一批扣走——帳本總和仍然正確，
**歸屬完全錯了**：顧客損失的是他本來就該有的錢，留下的是他不該有的錢。

今天走不到（累積在付款完成才發生，取消只允許 pending 的訂單），
所以這是一個結構問題而不是一筆災情。

## 決策

`loyalty_reward_entries` 的負分錄可以**指名批次**：`batch_id` 指向那一批的入帳分錄。

- **有指名**：只扣那一批，而且**不看生效與到期**。還沒生效正是取消訂單要扣的情況；
  已經過期代表那一批從來沒被用掉，不扣的話那筆錢會一直掛在「已過期」上，
  而帳本總和已經因為這筆負分錄少掉了。扣不夠的部分丟掉，**不算 `shortfallCents`**——
  那一批已經被花掉是回沖的合法結果——但要計進 `unappliedClawbackCents` 回報出來。
- **沒指名**：照 ADR 0019 的先到期先用，而且只扣當下已生效、未過期的批次。
  扣不到就是帳本壞了，記進 `shortfallCents`。

`rewardService.reverseForOrder` 的扣回一律指名。折抵與手動調整維持不指名。

推導那一端因此不再需要認得 `source` 字串：判準從 `source === 'reversal'` 換成
「有沒有 `batchId`」。來源是服務層的詞彙，推導不該依賴它。

既有的扣回列由 migration `0005_backfill_clawback_batch` 回填而不是留一條相容路徑
（結構的部分在 `0004_clawback_names_batch`，兩者分開是因為 DDL 的鎖會持有到交易結束，
擠在一起等於讓那段全表掃描期間整張表讀寫全停）：
`reference` 是 `clawback:<orderId>`，對應的累積是 `(source='order-accrual', reference=<orderId>)`，
一對一查得到。留兩條路徑的代價是 `deriveRewardBalance` 從此要同時說明兩種扣回，
而它是這個模組唯一複雜的地方。

## 考慮過的選項

- **扣回指名的批次剩不夠時，回頭掃別批補足。** 否決：那正是這篇要修的行為，
  只是換成在邊緣情況才發生——更難發現，不是更安全。
- **不加欄位，改用 `reference` 反查那張單的累積分錄。** 否決：推導會因此需要
  「訂單」這個概念，而它現在只認得批次與金額。指名一個 id 才是這件事的本體，
  `clawback:<orderId>` 只是它今天恰好長成的樣子。
- **改成把原本那一列的剩餘量改掉。** 否決：那就是 ADR 0019 拒絕過的「就地加減」，
  帳本會退化成餘額欄位的複雜版本。
- **等部分退貨進模型時再一起做。** 否決：那時候這件事會混在一堆新東西裡，
  沒有人會記得它是舊的；而現在它是一個獨立、可驗證、走不到災情的改動。

## 後果

- `deriveRewardBalance` 多一個分支，但少一個對 `source` 字串的依賴，淨複雜度沒有增加。
- `batch_id` 是模組內的自我參照，依 ADR 0021 加了約束——錯誤的指名在推導裡會安靜地變成
  一筆扣不到任何東西的負分錄，那是寫入錯誤，不該等到讀餘額的時候才發現。
  資料庫擋掉三種：指名別位顧客的批次（複合外鍵 `(batch_id, customer_id)`）、
  指名自己、正分錄帶 `batchId`。第四種「指名另一筆負分錄」外鍵表達不了
  （部分唯一索引不能當外鍵目標），由 `unappliedClawbackCents` 揭露。
- **這條決策改寫了 ADR 0019 的守門員**。指名讓扣回搆得到未生效與已過期的批次，
  那部分是變好了；但它同時新增了一種先到期先用不會發生的情況——指名的批次已經被
  折抵掉時，扣不到的部分不去別批補，推導值於是高於帳本總和。不變式因此從
  「帳本總和 = 可用 + 未生效 + 已過期」變成
  **「可用 + 未生效 + 已過期 = 帳本總和 + `unappliedClawbackCents`」**，
  而它仍然是永真的。不去別批補是這個決策的本體，把差額說出來才是它欠的東西：
  `rewardService.balanceFor` 以 `warn` 記它（`shortfallCents` 走 `error`，
  那是帳本壞了；這個只是錢已經花掉）。
- 部分退貨進模型時，「退這一批的多少」已經表達得出來，不必再動結構。

## Falsified if

`packages/commerce/loyalty/src/balance.ts` 的 `usableBatchesFor` 讓指名的扣回在扣不夠時
掃到別的批次、或 `packages/commerce/loyalty/src/service.ts` 的 `reverseForOrder` 寫出
不帶 `batchId` 的扣回、或 `packages/commerce/loyalty/src/schema.ts` 拿掉 `batchId`
—— 任一項成立，代表扣回又回到「先到期先用」，這篇記的理由要重新檢視。
