# 94 — 登入與登出走模組宣告的頁面

**What to build:** 使用者從前台表單登入、登入前放進購物車的東西跟著帶進來、按登出就回到首頁——這條路從此走模組宣告的頁面，而不是 controller 上的 decorator。新增一個由 release 組裝的認證模組，購物站先接上它。

順手兌現兩件契約上早就寫著、實作卻另有一套的事：登入後的轉址目的地由路由層統一清洗（只接受同源的站內路徑），以及已經登入的人打開登入頁會被帶回原本要去的地方，而不是又看到一次登入表單。

**Status:** done

## 實作時一併改掉的小事

- 登入失敗的訊息從「電子郵件或密碼不正確。」改成「登入失敗：請確認電子郵件與密碼。」
  兩者都中性、都不洩漏帳號是否存在，換的只是語氣。
- 路由層對「已經是真身分但不符這一頁 audience」改回 403，不再送去登入頁——否則會與
  登入頁的「已登入就轉回來」互踢成無限轉址。
- 誰算「已經登入」由 release 指定（購物站是 `customer`），不是寫死成所有 actor type。

## 工單 93 轉過來的三個待決（本票已決）

- **登出頁的 CSRF**：現行表單登出刻意標 `@Anonymous()`，理由是「被強制登出是干擾而不是資料外洩」。
  資料驅動的路由只在 class 上掛 `Public()`，沒有 per-page 的匿名旗標——session 有效但沒帶
  `_csrf` 時會回 403 而不是登出。要嘛 theme 的登出表單一律帶 `_csrf`，要嘛頁面宣告多一個旗標。
- **用 Bearer token 認證的呼叫端打登出**：沒有 cookie，所以什麼都不會作廢卻回 303 說登出了。
  這和今天的 `AuthController.logout` 行為一致，不是回歸，但這一票要決定它該回 400 還是無操作。
- **簽發失敗要不要回滾**：session 在 `resolve` 裡就已經寫進資料庫、cookie 也可能已掛上 reply，
  所以「簽發失敗等於沒登入」並不成立。目前的行為是不送 303、交給錯誤頁。
