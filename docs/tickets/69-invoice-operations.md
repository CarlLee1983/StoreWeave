# 69 — 電子發票的營運介面

**What to build:** 工單 66 的發票模組完全由事件驅動：付款成功開立、全額退款作廢，
但沒有 HTTP 端點也沒有後台頁面。開立失敗時營運只能進資料庫看。補上唯讀的查詢面與
一個明確受限的重試入口，讓「這張單開了沒、為什麼失敗、再送一次」在後台做得完。

**Blocked by:** —

**Status:** completed

- [x] 新增 `invoice:read` 與 `invoice:write` 到 staff 角色；`invoice:system-write` 維持只給背景工作
- [x] `/api/v1/invoices` 提供列表與單筆查詢，回應不含顧客個資與品項快照（那兩份仍只給 system query）
- [x] 重試只在 `issue_failed` 與 `void_failed` 兩個狀態開放，其餘狀態回 409
- [x] 重試重新排入既有的 job，dedupe key 帶上嘗試次數，不會被前一次的 key 吃掉
- [x] 後台頁顯示發票狀態、發票號碼、開立日期、嘗試次數、最後錯誤與重試入口
- [x] Bus integration 測到重試的狀態閘門與冪等；jsdom 測到重試只對失敗狀態出現

## 不做的事

- 店員手動開立一張沒有付款事件的發票，或手動作廢一張沒有全額退款的發票——
  兩者都會繞過工單 66 拍板的「發票生命週期由訂單與退款事件驅動」，要改得先有決策。
- 折讓（部分退款不送外部動作，同工單 66）、發票下載與寄送樣板。
- 「送出成功但回應遺失」的補救。`RelateNumber` 由固定的 reference 推出，重送會拿到重複拒絕，
  而目前沒有查詢介面問得到「這張到底開了沒」。這條開在[工單 70](70-invoice-issue-reconciliation.md)，
  與工單 64 同樣擋在商家開通上。
