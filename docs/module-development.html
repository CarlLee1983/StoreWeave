StoreWeave 模組開發指南

這份指南從一張空白目錄開始，寫出一個自己擁有資料表、有後台權限、會排背景工作、有前台頁面的模組，最後把它組進一個 Release 並用測試證明它能跑。範例是一個「講座報名」模組 workshop。

開工之前

先決定落腳處

StoreWeave 有三種擴充位置，選錯了會一路卡到底。倉庫的鐵則是 Core 永遠不改：品牌差異走 Theme，客戶特殊需求走 Extension，一塊有自己資料與規則的領域才寫成模組。

位置能做什麼做不到什麼典型例子
模組
PlatformModule		擁有資料表與 migration；handler 拿得到交易 ctx.tx；宣告 Command、Query、事件、Job、權限、前台頁面直接讀寫別的模組的資料表；只能透過對方匯出的 service 或 Command／Queryplatform-site、coupon、shipping
Extension
@storeweave/extension-sdk		提供金流、物流、發票、ERP provider；註冊 ext.<id>.* 的 Command／Query；訂閱事件沒有 migration，拿不到 tx 或 db（ADR 0029）；只能 import SDK 與 contracts（架構測試會擋）ecpay、demo-erp
Themepage id → renderer 的對映，把 view 畫成 HTML自己決定有哪些頁、自己查資料theme-base、default

判斷的快速問法：這個功能需要新的資料表嗎？需要就是模組。只是接一個外部服務、資料由它保管，就寫 Extension，照 docs/extension-development.md 做。本指南只談模組。

對照表

一個模組的全貌

模組就是一次 defineModule({...}) 呼叫，定義在 packages/platform/kernel/src/module.ts。平台只認得這份宣告：啟動時先驗證整張模組圖（ADR 0036），通過後才建立資料庫連線、註冊 handler。下表是每個欄位對應的步驟，以及宣告錯了會在哪裡被擋。

步驟 01

建立套件

最小、最適合照抄的真實模組是 packages/platform/site：兩張表、兩個 Command、一個 Query、一頁首頁，沒有別的。新模組照它的檔案分工：

接線要動兩個根設定：

  • tsconfig.base.json 的 paths 加 "@storeweave/workshop": ["packages/<產品>/workshop/src/index.ts"]。套件之間靠這條別名解析，site 的 package.json 裡一個相依都沒寫。
  • pnpm-workspace.yaml 目前只涵蓋 packages/platform|commerce|extensions|themes/*。新的產品目錄要補一條 glob。

型別檢查（packages/**/src）與單元測試（packages/**/test）的 include 已經涵蓋任何 packages 子目錄，不必改。

模組本身寫成工廠函式而不是常數，因為 release 組裝時常要傳選項（site 收 defaultNavigation、coupon 收時區與幣別）。version 一律讀 package.json：

步驟 02

資料表與 migration

資料表有兩份描述：schema.ts 給 Drizzle 查詢用，migrations.ts 是實際建表的 SQL。SQL 內嵌在 TypeScript 裡，打包後的 release 不需要額外檔案。

規則

  • id 模組內唯一、單調遞增，例如 0001_init、0002_add_venue。全域 id 是 <module>/<id>。已發布的 migration 不改內容：history 帶 checksum。
  • phase 是 Expand–Migrate–Contract：expand 必須讓舊版程式照常運作；migrate 搬資料；contract（刪欄、收緊約束）只能在舊版不再需要回滾之後發布。
  • 表名加模組前綴，並全部列進 data.owns。名稱須符合 ^[a-z][a-z0-9_]*$，兩個模組宣告同一張表會在啟動前被拒絕。
  • 預設資料不寫進 migration。site 的註解說明了原因：寫進去之後，店家刪掉的項目會在下一次遷移後復活（ADR 0046）。預設值由 release 組裝時傳入。
  • 跨模組外鍵先讀 ADR 0021。

步驟 03

權限

模組只宣告權限鍵；誰擁有它由 release 的角色目錄決定。每個 Command 與 Query 都指向一個權限鍵，Command Bus 在開交易之前就檢查。

owner 寫錯時，模組圖驗證會丟 permission "…" has owner "…", expected "workshop"。把權限發給角色是步驟 09 的事。

命名沿用既有慣例：<領域>:read、:write、:manage，前台匿名可讀的用 :public-read（例如 site:public-read、content:public-read）。

隱藏選單不是權限檢查。後台看不到入口、前台沒有連結，都不能取代 descriptor 上的 permission。直接打 URL 的請求一樣要被後端擋下。

步驟 04

Command 與 Query

所有寫入都走 Command Bus，所有讀取都走 Query Bus。Controller、前台頁面、Job 與 MCP 工具都是呼叫端，沒有一個拿得到 repository。Command 的完整路徑依序是授權、Zod 驗證、Idempotency、開交易、handler、Audit、Outbox，全部由 Bus 處理。

handler 拿得到什麼

Context欄位
CommandContextactor、tx（交易）、logger、correlationId、now，以及三個同交易動作：publish(event)、audit(entry)、enqueue(job)
QueryContextactor、db、logger。讀取沒有交易，也不能發事件

規則

  • input 一律 .strict()，而且是平的 object（ADR 0024）。漏掉 .strict() 或用 union／array 當 input，HTTP 橋接讀不出它宣告了哪些鍵，契約測試會失敗。
  • 名稱是公開契約。慣例是 <context>.<aggregate>.<action>，改名等於破壞呼叫端；要改形狀就提高 descriptor 的 version。
  • idempotency 有 required、optional、none 三種。會造成外部副作用或金額變動的寫入用 required，沒帶 key 的呼叫直接被拒絕。
  • 範圍過濾留在 handler。「只列出我自己的報名」這種限縮依 ctx.actor 在 handler 內做，不靠呼叫端加條件。
  • 錯誤丟 PlatformError（如 PlatformError.validation(...)）。Zod 驗證失敗由 Bus 轉成 VALIDATION_ERROR，不會變成 500。

步驟 05

事件與訂閱

事件是模組之間最鬆的耦合：發出的一方不知道誰在聽。事件名稱須符合 ^[a-z][a-z0-9]*(\.[a-z][a-zA-Z0-9]*)+\.v[0-9]+$，也就是 <context>.<aggregate>.<action>.vN；defineEvent 當場檢查。發出的事件列進模組的 events。

訂閱別人的事件時，投遞經過 Outbox 與背景工作，所以訂閱者失敗不會讓發出事件的交易回滾。這是機制本身的結果，不需要額外處理。代價是訂閱者一定會遇到重複投遞，要自己靠去重鍵擋。下面是 coupon 模組在新會員註冊時發券的寫法：

  • 訂閱者可以執行自己模組的 Command；要執行別的模組的 Command，得在 commands 列出精確的 { from, name, version }，而且對方必須是你的相依。
  • 訂閱只驗證事件存在，不構成初始化順序的相依（ADR 0036）。
  • 要寄通知就用 bindPorts 取得 ports.notifications，不要自己 import 通知模組的內部實作。coupon、loyalty 都是這樣寫，並且在 dependencies.required 列出 platform-notifications。

步驟 06

背景工作與排程

Job 是佇列裡的一筆資料，由 Worker 行程取出執行；平台沒有任何 in-process timer，行程重啟不會遺失排程狀態（B05）。範例：每天台北時間凌晨三點，把已經開場的場次關掉。

schedule 寫法payload適合
{ everyMs }{ bucket, scheduledFor }固定間隔，切片對齊 UTC epoch。cart、coupon 的每日工作都用它
{ cron, timezone }{ scheduledFor }本地午夜、月底、每月第一個週一。timezone 必填，DST 行為不靠行程的本地時區猜
  • 兩種寫法都能加 catchUp（停機後最多補排幾次，預設 1）與 overlap（上一次還沒跑完時 queue 或 skip，預設 queue）。
  • jobContractV1 請一定要寫。沒有它的 job 在 payload cutover 時會被擋下：Job payload cutover blocked: … without jobContractV1 metadata。之後改 payload 形狀時，保留舊版本的 schema 並提高 currentVersion。
  • 外部副作用用 ctx.idempotencyKey（等於 occurrenceId）。它在重試與 lease 回收之後都不變。
  • 長時間的工作要聽 ctx.signal。逾時、關機、失去 worker 所有權時會 abort。
  • 不是排程、而是某個 Command 之後才要做的事，在 handler 裡用 ctx.enqueue({ type, payload, dedupeKey })，它和寫入在同一個交易。

步驟 07

前台頁面與 Theme

頁面由擁有資料的模組宣告，Theme 只負責把 view 畫出來（ADR 0045）。模組決定路由、輸入與權限，Theme 決定長相；兩邊用 page id 對上。

resolve 拿得到什麼

PageResolveContext 刻意只給受限入口：queries、commands、actor（未登入時是 release 的匿名 actor）、locale、clientKey（來源端雜湊，節流用它而不是 actor.id）、cookies（只有訪客購物車 token 兩個動作）、providers（唯讀）。拿不到 runtime、資料庫、logger 或請求物件。ADR 0045 的 Falsified if 條件就守著這件事。

結果 PageOutcome 有五種：view、redirect、session-start、session-clear、not-found。登入、登出這類要動 session 的頁面回傳結果，由路由層執行（ADR 0047）。

Theme 端

Theme 用 defineTheme<Pages> 宣告它服務哪些模組的頁面，型別參數讓每個 renderer 收到的 view 型別被逐一比對。顯示與送出失敗重畫的是同一張表單，因此兩個 id 共用一個 renderer，theme-base 的認證頁也是這樣寫。

缺頁在啟動時拒絕，不在請求時 404。載入了 workshop 模組、Theme 卻沒有 workshop.sessions.index 的 renderer，release 會拒絕啟動並列出缺哪些 page id。只做寫入與轉址、沒有畫面的頁面設 required: false。
  • 所有插進 HTML 的字串都經過 escapeHtml。Theme 是純字串 SSR，不會替你跳脫。
  • page id 慣例是 <模組>.<領域>.<動作>，全域唯一。同一個 method + path 被兩個模組宣告時組裝就報錯。上例 GET 與 POST 共用 /workshops 是合法的。
  • audience: 'customer' 或 'operator' 的頁面，未登入會被導向登入頁。寫入頁面通常要用 loginNext 指回它的顯示頁。

步驟 08

JSON API

後台與外部呼叫端走 REST。Controller 不寫邏輯，只宣告「這條路由對應哪個 Command 或 Query」，其餘交給 BusController.rest。宣告式契約 @HttpContract 會在啟動時做靜態檢查。

寫好之後，把它加進該 release 的 httpAdapter.controllers(...) 回傳陣列，也就是 apps/api/src/releases/<release>.ts。Query string 帶數字或布林時，要在契約上加 queryEncoding，例如 { limit: 'number' }。

步驟 09

組進 Release

Release 是「這一版編進了哪些模組、角色、Theme、Extension」的靜態清單，沒有執行期探索。最乾淨的做法是新開一個 release，不動 base 與 commerce：

平台自己的模組（platform、platform-identity、platform-mail、platform-notifications、platform-storage、platform-cache、platform-ops）由 runtime 自動加入，createModules 只列產品模組。

讓建置認得新的 release id

  • scripts/releases.mjs：新增 workshop 項目，填 runtime、http、seed、admin、themeAssets 五個欄位。
  • scripts/build-release.sh：case "$RELEASE_ID" 目前只接受 commerce 與 base，其餘一律 Unknown release，要補一條。
  • apps/api/src/releases/workshop.ts：HTTP adapter，releaseId 必須等於 release 的 id，否則 API 啟動時會丟 HTTP adapter does not match the selected release。
  • 以 STOREWEAVE_RELEASE=workshop pnpm build:release 建置。tsconfig.base.json 的 @storeweave/selected-* 別名預設指向 commerce，建置腳本會依環境變數換掉。

後台頁面

後台路由目前是編譯期的一份表：apps/admin/src/routes.tsx 的 ENTRIES。新增一頁就是加一列，填 path、permissions、module: 'workshop'（模組沒載入就不顯示）、section、icon、i18n 的 navLabel／title／subtitle 鍵，以及 render。注意 releases.mjs 裡只有 commerce 的 admin: true，見文末〈目前的邊界〉。

步驟 10

測試與完成

純函式放 packages/…/workshop/test/，由 unit 專案收進來。牽涉資料庫、交易、Worker 的行為寫整合測試，放 tests/integration/。整合測試用 testcontainers 起 PostgreSQL，本機要有 Docker。最接近真實啟動路徑的寫法是 bootstrapRelease，照 tests/integration/base-release.test.ts：

值得寫成測試的事

  • migration 跑兩次，第二次回傳空陣列。
  • 每個 Command 的權限：有權限的角色成功，沒有的收到 Forbidden。匿名訪客的權限要特別測。
  • 未知欄位被 .strict() 擋下，回的是驗證錯誤而不是 500。
  • 事件真的寫進 Outbox，訂閱者重複投遞時只產生一次效果。
  • 前台頁面：POST 成功回 303、驗證失敗回 400 並重畫表單、使用者輸入被跳脫。
  • 換一個缺 renderer 的 Theme，release 拒絕啟動。
完成的定義是 make verify 通過。它依序跑型別檢查、後台型別檢查、unit、admin、integration。vitest.config.ts 設了 fileParallelism: false，整合測試要跑二十分鐘以上，放背景跑。中途可以先用 make typecheck、make test 拿快速回饋，但 unit 全綠、integration 卻失敗的情況發生過（工單 99）。

寫給現在的讀者

目前的邊界

以下是 86d87a8 時點尚未完成、會影響模組寫法的地方。遇到了照這裡做，不要自己發明替代方案。

  • 後台頁面不是模組宣告的。前台頁面由模組的 pages 帶進來，後台仍是 apps/admin/src/routes.tsx 的編譯期清單，而且 releases.mjs 只有 commerce 打包後台。非商務 release 要有後台，需要先有一次邊界決策。
  • 使用者上傳的圖片先不要做。媒體管理（B10）正在進行；文章配圖目前是 Theme 擁有的 image key（ADR 0034），這條 ADR 會在 B10／B14 完成後被取代。新模組不要依附 Theme image key。
  • 快取與檔案儲存透過 runtime 的 cacheBindings／storageBindings 在組裝時綁定到模組 id，模組只拿得到自己的 scope。這兩條路徑還沒有非商務範例，B16 會補上。
  • member 角色登入後看得到什麼，包括站內收件匣，尚未決定，排在 B14。
  • 這份指南本身預計由 B16 驗證：接手者照文件只新增模組與站點組裝，不改 base。範例程式碼屆時會換成通過 make verify 的版本。

動到模組邊界、公開介面或不變條件之前，先讀 docs/adr/；詞彙以根目錄 CONTEXT.md 為準。
