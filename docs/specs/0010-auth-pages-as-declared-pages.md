# Spec 0010 — 認證頁面成為模組宣告的頁面

- 日期：2026-09-10；程式盤點基準：`41a691c`（B13 合併後）。
- 狀態：ready-for-agent。
- 決策來源：[ADR 0047](../adr/0047-session-is-a-page-outcome.md)（session 是頁面的 outcome），
  前置決策 [ADR 0045](../adr/0045-modules-declare-storefront-pages.md)、
  [ADR 0046](../adr/0046-site-settings-and-navigation-are-release-data.md)、
  [ADR 0041](../adr/0041-base-accounts-are-not-commerce-customers.md)。
- 詞彙依根目錄 `CONTEXT.md`：Account、Member、Session、Customer、顧客前台（Storefront）。

## Problem Statement

B13 把前台頁面從 Theme 搬到模組宣告，但登入、註冊、忘記密碼、重設密碼這四頁搬不過去。
原因是頁面能碰的 cookie 只有訪客購物車那兩個具名動作，而登入要簽發 Session。結果是：

形象站（base release）的前台沒有登入入口。Theme 已經畫得出登入表單、角色目錄也有可以
自助註冊的 Member，但沒有路由把它們接起來，所以一個用 base release 建的網站沒辦法讓人登入。

平台層的頁面清單還留著一個商務無關卻又不屬於任何模組的特例。每個 Theme——包括一個只想
做形象站的 Theme——都必須實作一個四模式的認證版型，否則無法通過啟動檢查。

認證路由與其他前台路由長得不一樣：一邊是資料驅動的頁面宣告，一邊是 decorator，兩者的
轉址清洗、節流宣告與 cookie 效果各有一套寫法。同一件事有兩種做法時，新的頁面會照著看到
的那一種寫，而錯的那一種比較顯眼。

## Solution

這四頁變成由模組宣告的普通前台頁面，和購物車、聯絡我們沒有兩樣。頁面不簽發 Session——
它把「請簽發 Session 並轉到這裡」當成渲染的結果交出去，由路由層執行。

對建站的人來說，形象站從此有可用的登入、註冊與密碼重設流程，而且和購物站是同一份實作。
對 Theme 作者來說，認證版型變成「有載入認證模組就要提供」的 renderer，不再是所有 Theme
的無條件義務。對接手的開發者來說，前台只剩一種路由寫法。

## User Stories

1. 作為形象站的訪客，我要能在網站上找到登入頁並登入，這樣我才能看到只有我看得到的東西。
2. 作為形象站的訪客，我要能自己註冊一個 Member 帳號，這樣我不必等店家替我開帳號。
3. 作為形象站的 Member，我要能登出，這樣我在公用電腦上不會把帳號留給下一個人。
4. 作為忘記密碼的 Member，我要能在前台送出信箱收到重設連結，這樣我不必聯絡客服。
5. 作為拿到重設連結的 Member，我要能設定新密碼並被帶到登入頁，這樣我知道接下來該做什麼。
6. 作為購物站的訪客，我要在登入後看到我登入前加進購物車的商品，這樣我不必重新挑一次。
7. 作為購物站的訪客，我要在登入後看到「有哪幾件商品因為下架而沒被帶過來」，這樣我不會以為系統吃掉了我的東西。
8. 作為購物站的訪客，我要在註冊完成的同時就是登入狀態，這樣我不必剛註冊完又登入一次。
9. 作為已經登入的人，我打開登入頁時要被帶回我原本要去的地方，這樣我不會以為自己被登出了。
10. 作為從結帳頁被要求登入的顧客，我要在登入後回到結帳，這樣我不必重新找一次購物車。
11. 作為被釣魚連結帶到登入頁的使用者，我要在登入後只會停在這個網站內，這樣別的網站拿不到我的 Session。
12. 作為把密碼打錯的使用者，我要看到登入頁重新出現並附上錯誤訊息，而且信箱欄位還留著我填的值，這樣我不必整份重打。
13. 作為不存在的帳號的輸入者，我要得到和密碼錯誤一樣的回應，這樣攻擊者無法用它掃出哪些信箱註冊過。
14. 作為送出忘記密碼的人，我要不論信箱存不存在都得到同一句中性訊息，這樣別人無法用它探測會員名單。
15. 作為註冊時填了既有信箱的人，我要得到中性的失敗訊息，這樣它不會變成帳號枚舉的管道。
16. 作為網站的營運者，我要登入與忘記密碼都有節流，這樣線上暴力破解與寄信轟炸都打不穿。
17. 作為網站的營運者，我要節流以來源端為鍵而不是以帳號為鍵，這樣一個人灌爆不會把其他人一起擋掉。
18. 作為網站的營運者，我要前台表單的登入在別的網站送過來時被拒絕，這樣沒有人能替我的使用者植入 Session。
19. 作為 Theme 作者，我要只在網站載入了認證模組時才需要提供認證版型，這樣我做一個純展示的 Theme 不必寫登入表單。
20. 作為 Theme 作者，我要登入、註冊、忘記密碼、重設密碼各自拿到只屬於它的資料形狀，這樣我不必在 renderer 裡判斷現在是哪一種模式。
21. 作為 Theme 作者，我要在網站啟動時就被告知我少提供了哪個版型，而不是等某位訪客按下按鈕才發現，這樣缺頁是我的問題而不是客人的問題。
22. 作為 Theme 作者，我要能讓一組 GET 與 POST 頁共用同一個渲染函式，這樣我不必為同一個畫面寫兩份。
23. 作為模組作者，我要能宣告一個會簽發 Session 的頁面，而不必拿到請求或回應物件，這樣我的頁面仍然可以用純函式的方式測試。
24. 作為模組作者，我要 Session 的簽發在契約上看得見，這樣「這個端點會動到哪些 cookie」不是靠讀實作得知。
25. 作為 release 的組裝者，我要自己決定這個網站有沒有登入頁，這樣一個完全公開的網站不會被塞進一組沒人用的路由。
26. 作為 release 的組裝者，我要指定註冊走哪一個命令，這樣購物站的註冊可以同時建立 Customer，而形象站只建立 Account。
27. 作為購物站的組裝者，我要註冊時的 Account 與 Customer 在同一筆交易裡建立，這樣不會留下一個沒有 Customer 的孤兒帳號。
28. 作為形象站的組裝者，我要登入流程不要求我載入購物車模組，這樣我的網站不必為了登入而帶進商務資料。
29. 作為接手這個 repo 的開發者，我要前台只有一種路由的寫法，這樣我照著任何一頁抄都不會抄到已經被淘汰的做法。
30. 作為接手這個 repo 的開發者，我要轉址的清洗只有一份實作，這樣不會有某個模組漏掉它。
31. 作為 API 的呼叫端，我要 REST 的登入與登出行為不變，這樣這次搬遷不會弄壞我的整合。
32. 作為後台的操作者，我要我的登入與第二因素流程不受這次改動影響，這樣搬遷的風險留在前台。

## Implementation Decisions

**新增一個認證模組，由 release 組裝。** 模組名 `platform-auth`，工廠接一個註冊命令參數。
它宣告這九個頁面：登入的 GET 與 POST、註冊的 GET 與 POST、忘記密碼的 GET 與 POST、
重設密碼的 GET 與 POST、登出的 POST。`platform-identity` 維持原狀——它繼續持有認證服務，
繼續不宣告任何頁面，也繼續由 kernel 直接掛載而不進 release 的模組清單。

沒有讓 `platform-identity` 宣告這些頁面：它不由 release 組裝，那會讓「頁面集合由 release
決定」出現永久的例外。也沒有併進 `platform-site`：那個模組是導覽與網站設定的擁有者。

**Session 是頁面的回傳值。** 頁面的 outcome 型別新增兩個具名變體，一個帶著已簽發的
Session 與轉址目的地，一個只表示清除。頁面解析的 context 不新增任何欄位。路由層收到這兩
種 outcome 時負責寫 cookie、合併訪客購物車、送出轉址。契約上既有的 cookie 效果詞彙與這兩
個變體同名。

**訪客購物車的合併留在路由層，並且只有一份實作。** Release 的 HTTP adapter 上已經有一個
開始 Session 的 hook，但目前被三個呼叫端繞過而直接引用購物站的實作。這次把三處都改回經過
adapter，並移除 base release 那份不合併購物車的重複實作——合併與否成為「這個 release 有沒
有購物車模組」的自然結果。消除這些繞過是 ADR 0047 能轉 accepted 的前置條件。

**註冊命令由 release 指定。** 購物站傳入建立 Customer 的命令（它在同一筆交易裡建立 Account
與 Customer），形象站不傳、走認證服務自己的註冊。角色目錄已經規定一個 release 至多一個可
自助註冊的角色。

**base release 取得登入頁。** base 的 Theme 已經有認證版型、角色目錄已經有 Member，這次補
上路由與模組。

**認證版型拆成四個。** 現行的四模式聯集型別拆成四個各自獨立的 view 型別。Theme 的 renderer
對照表多八個鍵，實際渲染函式仍是四個——同一個函式掛在 GET 與 POST 兩個鍵上已經是既有做法。
登出頁宣告成不需要版型（只轉址、沒有畫面）。平台的系統頁清單從此只剩錯誤頁。

**轉址目的地的清洗上移到路由層。** 契約上早就宣告「只接受同源的驗證過路徑」，實作卻在
controller 的私有函式裡。搬遷後由路由層統一清洗，頁面拿到的已經是安全的站內路徑。

**已登入者打開登入頁改為轉址。** 頁面解析時已經拿得到 actor，判斷屬於頁面自己。

**REST 的登入與登出不動。** 它們的呼叫端要 JSON、前台表單要 303，合併只會逼出一個判斷
Accept header 的分支。前台登出的 CSRF 豁免在工單 94 被**直接拿掉**而不是變成可見的宣告——理由與代價記在
[ADR 0047](../adr/0047-session-is-a-page-outcome.md)。

**前台角色不處理第二因素的強制註冊。** 目前只有營運者系的角色要求第二因素。哪天前台角色
也要求了，判斷屬於頁面而不是路由層。

## Testing Decisions

好的測試在這裡的意思是：斷言從外面看得到的行為——HTTP 狀態碼、轉址目的地、cookie 有沒有
被簽發、頁面有沒有出現該出現的欄位、啟動有沒有被拒絕——而不是斷言某個函式被呼叫過幾次，
也不是斷言 outcome 物件的內部欄位排列。搬遷的價值就在於外部行為不變，所以既有案例本身
就是這次改動的回歸網，改它們要有明確理由。

**四個既有接縫，不新增接縫。**

最高的接縫是 `tests/integration/auth-http.test.ts`。它已經用 harness 加真實 server 的
`inject` 覆蓋前台表單登入的跨站拒絕、同源成功、轉址只接受站內路徑（包含 `/\`、`//`、
定位字元等繞過寫法），以及登入與忘記密碼的節流。這次在這裡補：登入後 Session cookie 仍然
簽發、訪客購物車仍然合併並帶出下架提示、已登入者打開登入頁被轉址、註冊完成即登入、
重設密碼成功後轉到登入頁、登出清掉 cookie。

`tests/integration/base-release.test.ts` 與 `tests/integration/base-http.test.ts` 補形象站
的登入流程：base release 的登入頁存在且可用、註冊只建立 Account 而不建立 Customer、
登入不要求購物車模組。

`packages/platform/kernel/test/page-registry.test.ts` 已經有十個案例守著頁面註冊與「Theme
缺必需頁面就拒絕啟動」，包括訊息要列出缺哪幾頁、`required: false` 缺 renderer 不阻擋啟動。
這次在這裡守：系統頁清單只剩錯誤頁、新的兩種 outcome 變體被路由層接受。

新增 `packages/platform/auth/test/pages.test.ts`，沿用 `packages/commerce/*/test/pages.test.ts`
的既有寫法：自己組一個頁面解析 context、直接呼叫 `resolve`、斷言回傳的 outcome。這一層的
重點是證明頁面**沒有**碰任何 cookie——簽發是回傳值，所以這些測試不需要請求或回應物件。

`packages/themes/base/test/base-theme.test.ts` 與 `packages/themes/default/test/default-theme.test.ts`
跟著 renderer 拆開改；`packages/themes/default/test/escaping.test.ts` 的認證表單轉義案例
要確認仍然覆蓋拆開後的四個版型。

**會被連帶震到的數字型斷言。** `tests/unit/release-manifest.test.ts` 斷言模組數是 22，
多一個認證模組之後要改。依 B13 的經驗，改動 release 組裝還會震到 release 設定、
release artifacts、release transition、release roles、CLI 輸出、base HTTP 與 HTTP/MCP
這幾支的 controller 數、route 數、migration 數與角色權限清單——新增模組時直接把這幾支一起
看，比等完整 integration 跑完報錯快得多。

**不重複測的**：`tests/integration/cart-merge.test.ts` 測的是合併命令本身的語意（取較大
數量、下架商品移除、訪客車失效），搬遷不改那個命令，所以這支不動。

## Out of Scope

Member 登入之後看得到什麼——特別是站內收件匣要不要給它——不在這份規格裡。那是授權面的
決定，已經釘在 B14 的派工卡上。

前台角色的第二因素。營運者後台的 MFA 流程不在這次改動範圍，前台角色目前也不要求它。

第三方登入、記住我、信箱驗證流程的改動。

Theme 的視覺改版。這次只改 renderer 的切分方式與資料形狀，不改任何版型的外觀。

REST 登入與登出的行為或形狀。

## Further Notes

ADR 0047 的 falsification 條件有一條目前就是違反狀態：開始 Session 的 hook 被三個呼叫端
繞過。實作時必須先消除這些繞過，否則這份決策一落地就自我否證。這不只是潔癖——形象站那份
不合併購物車的重複實作正是因為沒有人真的透過那個 hook 走，才會長出來而沒被發現。

整跑完整 integration 要獨占機器約 30 到 40 分鐘，而且跑的時候不要改 `apps/api` 或
`packages/**` 的原始碼（release artifacts 會在中途建置 admin bundle）。不要同時跑兩個
integration suite——B13 這樣做過一次，結果是一整批假紅與逾時；工單 94 又踩了一次，
`worker-recovery` 整批假紅，單獨重跑就全綠。

**在這台 16GB 機器上一次跑完整套會被系統因記憶體不足中止**（工單 94 連續踩兩次，
降到兩個 worker 也一樣——整套跑下來記憶體只增不減）。改成每 15 檔一批、依序跑，
每批結束釋放記憶體，就跑得完。

新增 workspace 套件時 `pnpm-lock.yaml` 要手動補 importer 條目：本地安裝不會補（沒有相依的
新套件在它眼裡不算變更），只有 Docker 的 frozen lockfile 會炸。`tests/unit/dockerfile-workspaces.test.ts`
已經有守衛，現在 unit 階段就會擋下來。
