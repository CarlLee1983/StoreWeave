# Spec 0012 — Dining Product Release

- 日期：2026-09-26。
- 狀態：ready-for-agent；已完成需求訪談，尚未拆成 Story 或開始實作。
- 產品邊界：[ADR 0053](../adr/0053-dining-is-a-separate-product-release.md)。
- 詞彙依根目錄 `CONTEXT.md`：Dining Release、餐廳訂位申請、餐廳訂位、桌型、占桌時長、用餐人數。

## 1. 目標與範圍

Dining 是與 Commerce、住宿 Booking 分開建置、部署並使用資料庫的 Product Release。首版服務單一門市餐廳：
店家設定桌型、可訂時刻與占桌時長，訪客送出訂位申請，店家人工接受或拒絕，接受後通知顧客。
首版不收訂金、不處理付款，也不與 Commerce 的菜單或訂單連動。

## 2. 申請與訂位

1. 未登入訪客可申請；姓名、電話、Email 為必填，結果通知以 Email 交付。首版不提供匿名查詢頁；
   送出後前台顯示申請編號，並寄送已收到申請的 Email。店家接受後沿用同一編號作為訂位編號。
   同一次送出因網路重試或連點而重送時只建立一筆；顧客另一次明確送出可建立新申請，即使內容相同。
   顧客可填選填備註，例如兒童椅或無障礙需求；備註原文呈現給店家，不構成系統保證或自動分桌條件。
   公開申請入口對來源與收件地址設可調整的送出頻率限制；部署時須提供各自的正整數上限與時間窗，
   未設定不能啟動公開申請入口。超限時不建立申請，也不寄送確認 Email。
2. 顧客只能選餐廳開放的開始時刻，不輸入任意時刻。申請保存提交時的開始時刻、人數與占桌時長。
3. 待處理申請不占桌。多人可以申請同一剩餘名額；先被店家接受的申請取得名額，之後的申請須重新檢查供應。
4. 店家接受時重新檢查整段占桌期間的供應，成功才產生已接受訂位並占用桌型名額。容量不足時不能接受，
   申請仍待處理；店家可拒絕，或在系統外聯絡顧客後由顧客重新申請。
   顧客送出時須距開始時刻至少一小時（店家可調整）；店家可在開始前接受，開始後不能接受。
   開始後仍待處理的申請不自動結束，直到店家拒絕。
5. 店家拒絕時申請結束為已拒絕。拒絕時給顧客看的原因選填；未填時寄送一般拒絕通知。
   若過時申請已依保存期限匿名化，店家仍可拒絕，但不寄 Email；後台須顯示「個資已清除，無法通知」
   並留下拒絕操作的稽核紀錄。首版沒有「請顧客改時間」的系統狀態。
6. 已接受的訂位由店家在開始前取消並釋放桌型名額。顧客首版不自行取消或改期；改期以取消後重新申請處理。
   開始後不以取消改寫訂位，也不追蹤已到店、未到或用餐完成狀態。
7. 接受、拒絕後寄送 Email。店家取消已接受訂位時須填寫給顧客看的取消原因，並寄送取消 Email。
   寄送失敗不回滾店家的決定或桌位變動；後台可看見明確失敗並重試。寄送結果不明時標記為待人工確認，
   不自動重寄；具處理訂位權限的後台人員檢查並承擔可能重複寄送的結果後，可手動重送。
   重送須經產品中立的 Base Notification 能力，使寄信與通知狀態的證據一致，並留下操作者稽核紀錄。
   接受通知確認日期、開始時刻、用餐人數與編號，不對顧客承諾桌型。

## 3. 桌型與供應

1. 店家設定每種桌型的可容納人數與桌數。一筆訂位只占一張桌的桌型名額，不指定實體桌號、不併桌。
   每個可容納人數首版只有一種桌型。
   同時有多種桌型可容納時，按容量由小到大選當時可用的桌型；三人可使用四人桌，
   若四人桌已滿也可使用五人桌；六人不可拆占兩張四人桌。
   用餐人數是需要座位的總人數，需要兒童椅的嬰幼兒計入；首版不分成人與兒童。
2. 占用區間包含開始、不包含結束。例如 18:00 開始、占桌 90 分鐘的訂位，19:30 可接下一筆；
   期間只要重疊就不能重複使用同一名額。
3. 占桌時長由店家設定，包含用餐與清桌。申請與已接受訂位沿用各自保存的占桌時長；設定變更只影響新申請。
4. 店家設定每週固定可訂開始時刻、指定日期休息或覆寫，以及最早與最遠可訂的限制。
   預設只能申請至少一小時後、至多三十天後開始的時段，店家可調整。餐廳使用自己的時區；
   在該時區不存在或有歧義的當地開始時刻不開放訂位。設定變更不改寫既有申請或已接受訂位的時刻與占用區間。
   指定日期設定完整取代該開始日期的每週設定。占桌區間可以跨午夜，仍歸屬其開始日期；
   隔天休息不撤銷前一晚已開始的訂位。
5. 店家將某日期設為休息或關閉時段後，該時段既有待處理申請不能再接受；已接受訂位維持，須由店家逐筆取消。
6. 桌數減少或停用桌型不能使任何占桌區間尚未結束的已接受訂位，其同時占用量超過剩餘桌數；
   桌型容納人數的變更也不能使這些訂位的人數超過該桌型容量，否則設定變更被阻止。
   已結束訂位保留當時桌型資料快照，不阻止未來調整。
   接受、取消與桌型／時段設定變更共用一致的容量與時段檢查，並行執行也不能超賣或接受已關閉的時段。
7. 前台只提供目前至少有一種合適桌型可用的開始時刻；容量已被已接受訂位占滿的時段不能送出申請。
   待處理申請不扣容量，故同一剩餘名額仍可收到多筆申請。

## 4. 產品與資料邊界

1. 首版以單一 `dining-reservation` Product Module 擁有桌型、可訂時段、申請、已接受訂位及占桌規則。
   它可在內部劃分程式責任，但不將供應與訂位拆成公開的跨模組契約。
2. Dining 使用獨立的 Release 與資料庫，選用適用的 Platform／Base 認證、命令、通知等能力；
   不匯入 Commerce Order 或住宿 Booking Reservation 的領域模型。
3. 部署時必須設定正整數的個資保存天數，不能依賴隱含預設值；期限屆滿後匿名化不再需要的姓名、電話與 Email。
   實際保存天數由營運方於部署前決定。
   已拒絕申請從拒絕時、已取消訂位從取消時、已接受且未取消的訂位從預定用餐結束時起算；
   過時仍待處理的申請也從原定用餐結束時起算。到期後可保留無法識別個人的狀態統計，但不保留聯絡資料。
   保存期限涵蓋申請與訂位資料、自由文字備註、拒絕／取消原因、通知、寄信內容、排程工作與稽核資料中的個資。
   Dining 判定到期時刻並以不含個資的參照要求 Base 清除其擁有的通知與寄信資料；Base 只保留不含顧客識別資訊的
   必要去重與稽核證據。到期時尚待寄送或結果不明的 Email 不再寄送或重送，清除作業須與寄送工作協調。
   新的工作與稽核紀錄不得在清除後重新帶入顧客個資。
4. 餐廳已有申請或訂位後，不允許直接修改時區；若需修改，須另設明確的資料遷移流程。
5. 後台提供待處理申請、按日期查詢的已接受訂位，以及已拒絕／已取消紀錄；每筆可見通知狀態，
   依權限提供接受、拒絕、取消及人工重送。操作不得強制越過容量與開放時段限制。
   接受、拒絕、取消及設定變更皆記錄操作者、時間與結果。

## 5. 首版暫不處理

- 封鎖名單、惡意申請與長期未處理申請的營運管理功能；公開入口的基本頻率限制屬首版。
- 顧客自助取消、改期、候位、併桌與實體桌號分配。
- 到店、未到與用餐完成的營運狀態。

## 6. 驗收情境

1. 單一門市可設定桌型數量、每週開始時刻、日期例外、占桌時長、可訂範圍及時區；
   同容量桌型重複建立、已有申請後修改時區、會破壞尚未結束占桌區間的桌數或容納人數變更皆被拒絕。
2. 訪客只能對開放且仍有合適桌型的時段申請；同一次送出重試只建立一筆，另一次明確送出可建立另一筆。
   待處理申請不占桌，送出畫面與 Email 都提供同一申請編號。未設定來源與收件地址各自的正整數上限及時間窗時，
   公開申請入口不能啟動；超過限制時系統不建立申請、不寄 Email。
3. 店家接受時在同一個不可分割的操作中重查時段及完整占桌區間的容量；並行接受不能超賣。
   接受與桌數減少、桌型停用、容納人數變更或關閉時段並行時，也不能超賣或接受關閉時段。
   最小合適桌型已滿時可使用下一種合適桌型。容量不足或時段已關閉時，申請仍待處理。
4. 18:00 開始、90 分鐘的訂位允許 19:30 的下一筆；任何真正重疊的區間不能重複使用同一桌型名額。
   23:30 的訂位可跨午夜；隔天的休息設定不取消這筆訂位。
5. 店家只能在開始前接受或取消；拒絕申請可選填顧客可見原因，取消已接受訂位須填顧客可見原因。
   接受通知不揭露內部分配的桌型。開始後不能接受的待處理申請仍可拒絕；若其個資已到期清除，
   拒絕不寄 Email，後台顯示無法通知並記錄操作者與時間。
6. 明確失敗的 Email 可重試；結果不明的 Email 不自動重寄，後台標示待人工確認並允許有權限的人員手動重送。
   手動重送後 Base 寄信與通知證據一致。通知失敗不回滾已接受、已拒絕或已取消的業務狀態。
7. 後台清單可查待處理、已接受、已拒絕及已取消的紀錄與通知狀態，相關操作與設定變更可追溯操作者、時間與結果。
8. 設定的保存期限屆滿後，拒絕、取消、已過時的接受或待處理紀錄，以及相關通知、寄信、工作與稽核紀錄，
   不再保存顧客姓名、電話、Email、自由文字與其他可識別個資；必要的狀態、去重與稽核證據仍可追蹤。
   到期時未寄送或結果不明的 Email 不會在清除後送出。
