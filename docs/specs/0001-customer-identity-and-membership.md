# Spec 0001 — 顧客身分與前台會員

- 狀態：ready-for-agent
- 依賴：無（這是第一層，其餘規格都建立在它上面）
- 相關 ADR：0014（顧客身分）、0012（操作者身分）、0010（平台領域中立）

## Problem Statement

這個購物站現在沒有「顧客」。訂單上的 `customerEmail` 是一個沒人驗證的自由文字欄位，
下單的人與系統之間沒有任何持久關聯。顧客因此無法查自己的訂單歷史、無法累積任何東西、
無法收到任何針對他的優惠；而任何人只要猜到訂單號，就能讀到別人的訂單。

對經營者來說，這代表整個行銷層無處著力：優惠券發給誰、購物金累在誰身上、
生日禮券寄到哪裡，全都沒有答案。

## Solution

前台有真正的會員系統。顧客可以註冊、登入、登出、重設忘記的密碼、修改自己的資料，
並且只看得到自己的訂單。結帳必須先登入 —— 每一張訂單從此都有確定的歸屬。

後台操作者與顧客共用同一套帳號與 session 機制，但兩者是不同種類的人：
稽核紀錄分得出「店員改了這張訂單」和「顧客改了這張訂單」。

## User Stories

1. 作為一個訪客，我想要用 email 與密碼註冊成為會員，這樣我才能下單購物。
2. 作為一個訪客，我想在註冊時就知道 email 已經被用過，這樣我不用送出表單才發現。
3. 作為一個會員，我想要用 email 與密碼登入，這樣我可以回到我的帳戶。
4. 作為一個會員，我想在登入後保持登入狀態一段合理的時間，這樣我不用每次瀏覽都重登。
5. 作為一個會員，我想要主動登出，這樣在公用電腦上我的帳戶不會被別人使用。
6. 作為一個忘記密碼的會員，我想要用 email 收到重設連結，這樣我不用重新註冊一個帳號。
7. 作為一個會員，我想要密碼重設連結有時效且只能用一次，這樣連結外洩不會讓帳戶長期暴露。
8. 作為一個會員，我想在修改密碼後讓其他裝置的登入失效，這樣我懷疑帳號被盜時可以自保。
9. 作為一個會員，我想要維護我的個人資料（顯示名稱、生日、聯絡電話），這樣店家能提供對的服務。
10. 作為一個會員，我想要維護我的收件地址，這樣我下單時不用每次重打。
11. 作為一個會員，我想要看到我所有的歷史訂單清單，這樣我可以追蹤我買過什麼。
12. 作為一個會員，我想要點進任何一張我自己的訂單看細節，這樣我可以確認內容與狀態。
13. 作為一個會員，我**不**想要能看到別人的訂單，即使我知道對方的訂單號。
14. 作為一個訪客，我想在瀏覽商品時不必登入，這樣我可以先逛再決定要不要註冊。
15. 作為一個訪客，我想在按下結帳時被引導去登入或註冊，並在完成後回到我原本要做的事。
16. 作為一個店家經營者，我想在後台看到會員清單，這樣我知道我有多少顧客。
17. 作為一個店家經營者，我想在後台查看單一會員的資料與訂單，這樣我可以處理客服問題。
18. 作為一個店家經營者，我想要停用一個會員帳號，這樣我可以處理濫用。
19. 作為一個店家經營者，我**不**想要在後台看得到任何人的密碼，即使是雜湊後的。
20. 作為一個稽核者，我想從稽核紀錄分辨一個動作是店員做的還是顧客自己做的，這樣責任歸屬才清楚。
21. 作為一個開發者，我想要顧客的領域資料（生日、等級、點數）不出現在平台模組裡，這樣平台維持領域中立。
22. 作為一個開發者，我想要只有一套密碼雜湊與 session 實作，這樣安全性修補只需要做一次。
23. 作為一個店家經營者，我想要系統寄出的信件走一個可替換的服務商，這樣我換 email 供應商時不用改程式。
24. 作為一個會員，我想在密碼重設信寄出後看到「若該 email 存在我們已寄出」的中性訊息，這樣攻擊者無法用它枚舉帳號。
25. 作為一個會員，我想要登入嘗試被節流，這樣我的帳號不容易被暴力破解。

## Implementation Decisions

### 模組與歸屬

- 新增 `packages/commerce/customer` 模組，擁有顧客的領域資料：顯示名稱、生日、聯絡方式、
  收件地址、帳號狀態，以及後續規格會加上的會員等級與點數關聯。
- 認證機制**不重寫**。`packages/platform/identity` 維持唯一一套密碼雜湊（scrypt）、
  session 簽發與解析、CSRF token 推導。它只知道「這是一個帳號」。
- 兩者以 `Actor.id` 相連。customer 模組不碰 `platform_users`，identity 模組不知道生日是什麼。

### 身分模型

- `Actor.type` 的封閉聯集新增 `'customer'` 成員。所有既有的型別窄化處必須顯式處理它。
- `BUILT_IN_ROLES` 新增 `customer` 角色。它持有的權限僅足以：讀商品、讀庫存、
  建立與讀取訂單、讀寫自己的顧客資料。角色維持常數，不進資料庫（沿用 ADR 0012）。
- 既有的匿名 `storefront` 角色保留給未登入訪客瀏覽，但**移除它無範圍限制的 `order:read`**。

### 授權與資料範圍

- Resource ownership 不進授權層。授權層維持「只比對 permission 字串與 wildcard」。
- 「只能看自己的」由 query handler 依 `ctx.actor` 過濾：當 actor 是 `customer` 型別時，
  訂單查詢一律加上該顧客的條件；當 actor 是後台角色時不加。
- 這同時修復現有缺口：以訂單號查詢訂單不再對匿名或他人放行。

### HTTP 守衛

- `@Public()` 的語意從「強制匿名」改為「不需要 token」。守衛改成三段式：
  Bearer token → session cookie → 匿名 storefront actor。
- 前台路由因此能辨識登入者。既有掛著 `@Public()` 的端點必須逐一確認沒有依賴「一定是匿名」。
- 前台 session 沿用 httpOnly cookie 與 double-submit CSRF；前台的寫入端點受 CSRF 檢查。

### 通知

- 新增第四種 Provider kind：`notification`，與 payment / shipping / erp 並列在 Extension SDK 的
  provider 契約中。Core 只認得介面（寄出一封具名樣板信給某個收件者），實作是 Extension。
- 本規格提供一個開發用的 mock notification provider，與 mock-payment 同性質。
- 密碼重設是第一個使用者。後續規格的生日禮券通知會沿用同一個 Provider。

### 密碼重設

- 重設 token 只存雜湊，明文只出現在信件連結中；有時效、單次使用、使用後作廢。
- 請求重設的回應一律中性，不透露 email 是否存在。
- 重設成功或主動改密碼，都撤銷該帳號其他所有 session。

### 結帳前提

- `commerce.order.placeOrder` 的 `customerEmail` 自由文字輸入移除，下單者由 Actor 決定。
  這是既有契約變更，依 ADR 0006 處理事件與 Command 契約的版本。
- 未登入呼叫結帳一律拒絕。

### 後台

- Admin 新增「會員」頁：清單、單一會員詳情、停用/啟用。
- Admin 的路由由寫死的字串聯集重構成一份路由表資料結構，但**仍是編譯期的**。
  執行期可註冊的 Admin 擴充不在範圍內（ADR 0013 記下的技術債）。

## Testing Decisions

好的測試只驗外部行為：呼叫一個 Command / Query / HTTP 端點，斷言回傳值、資料庫狀態、
發出的事件與稽核紀錄。不斷言 handler 內部怎麼分支、不 mock 內部函式。

三個接縫：

1. **Command / Query Bus（integration）** — 顧客資料的建立與修改、訂單查詢的範圍過濾、
   稽核紀錄的 actor type。前例：`tests/integration/flow-catalog-inventory.test.ts`。
2. **HTTP（integration）** — 註冊、登入、登出、密碼重設全流程、session cookie 與 CSRF、
   `@Public()` 三段式守衛的每一段、以訂單號查別人訂單被拒。
   前例：`tests/integration/auth-http.test.ts`、`tests/integration/identity.test.ts`。
3. **Admin 元件（jsdom）** — 會員清單頁與詳情頁。前例：`apps/admin/src/pages/LoginPage.test.tsx`。

必要的迴歸測試：既有掛 `@Public()` 的端點在守衛語意變更後行為不變。
notification provider 用 Extension SDK 既有的 contract test 工具驗證，不連真的 SMTP。

## Out of Scope

- Email 驗證（註冊後確認信）。刻意不做：會擋住註冊轉換，而結帳已強制登入。
- 2FA、社群登入、OIDC。
- 過期 session 的定期清理、登入失敗鎖定帳號（ADR 0012 已記為未實作，本規格不處理）。
- 顧客自助取消訂單、退款。
- 會員等級與任何點數 —— 屬於 Spec 0005，本規格只在 customer 模組留下它們的落腳處。
- 購物車 —— 屬於 Spec 0003。本規格的結帳仍是既有的單一商品直接下單。
- 執行期可註冊的 Admin 路由。

## Further Notes

`storefront` 角色的無範圍 `order:read` 是一個**既有的**授權缺口，不是本次引入的。
它在這份規格裡被修掉，但修法依賴 `Actor.type` 的擴充，因此不能更早單獨處理。
若要在本規格之前先止血，唯一的短期做法是讓以訂單號查詢的端點額外要求 email 相符，
那是暫時性的，會在本規格落地時移除。

`POST /checkout` 目前的 idempotency key 是每次請求現產的 UUID，等於沒有保護，
重複送出表單會建出多筆訂單。本規格不修它 —— 正確的 key 來源是購物車 id，屬於 Spec 0003。
