# Spec 0004 — 優惠券與行銷碼

- 狀態：ready-for-agent
- 依賴：Spec 0001（顧客身分）、Spec 0002（定價引擎）、Spec 0003（購物車）
- 相關 ADR：0013（行銷是 Commerce 模組）、0015（訂單金額模型）

## Problem Statement

Spec 0002 的促銷活動人人適用，但真實的行銷需要「只有某些人、某些時候能用」的優惠：
新會員禮券、生日禮券、限量的公開折扣碼、跟名人合作發出的行銷碼。

這些需求表面上很不一樣，實際上共用同一個核心：一張憑證，指向一條定價規則，
有自己的生命週期，可能綁定某個人，可能限量，而且必須在高併發下不超發。

## Solution

兩層模型：**Promotion** 是規則（折什麼、條件、優先序、可否疊加），
**Coupon** 是一張具名的券，指向某個 Promotion，有自己的狀態。

這一套模型吃下所有情境：實發券是有擁有者的 Coupon；公開折扣碼是沒有擁有者的共用碼；
行銷碼是共用碼再加一個合作夥伴的歸因；滿額折則只需要 Promotion、沒有 Coupon。

## User Stories

1. 作為一個店家經營者，我想要建立一組公開折扣碼，這樣我可以在社群上宣傳。
2. 作為一個店家經營者，我想要自訂公開折扣碼的字樣，這樣顧客好記好打。
3. 作為一個店家經營者，我想要限制一組折扣碼的總使用次數，這樣我可以控制行銷預算。
4. 作為一個店家經營者，我想要限制每個會員只能用同一組碼一次，這樣不會被同一個人洗完。
5. 作為一個店家經營者，我想要設定折扣碼的有效期間，這樣過期後自動失效。
6. 作為一個店家經營者，我想要隨時停用一組折扣碼，這樣我可以緊急喊停。
7. 作為一個店家經營者，我想要批次發券給全體會員，這樣我可以做全站回饋。
8. 作為一個店家經營者，我想要新會員註冊時自動收到一張禮券，這樣我可以提高註冊轉換。
9. 作為一個店家經營者，我想要會員生日當天自動收到一張禮券，這樣我可以經營關係。
10. 作為一個店家經營者，我想要實發的券綁定特定會員，這樣別人拿到碼也用不了。
11. 作為一個店家經營者，我想要跟名人合作發出行銷碼，這樣我可以追蹤他帶來多少業績。
12. 作為一個店家經營者，我想要知道每一組碼帶來多少訂單與營收，這樣我知道哪一檔活動有效。
13. 作為一個店家經營者，我想要一張訂單最多只歸因給一個合作夥伴，這樣分潤不會有爭議。
14. 作為一個店家經營者，我想要用人工對帳的方式處理佣金，這樣我不必先建一套結算系統。
15. 作為一個顧客，我想要在結帳前輸入折扣碼並立刻看到金額變化，這樣我知道值不值得。
16. 作為一個顧客，我想在輸入無效的碼時得到明確原因（不存在／已過期／已用完／不符資格），這樣我知道怎麼辦。
17. 作為一個顧客，我想要看到我擁有的券清單與到期日，這樣我不會忘記用。
18. 作為一個顧客，我想在收到生日禮券時被通知，這樣我知道它存在。
19. 作為一個顧客，我想要移除已套用的碼並換一個，這樣我可以比較哪個划算。
20. 作為一個顧客，我想在券剛好在我結帳時被別人用完的情況下，得到清楚的失敗訊息而不是被扣了款才發現。
21. 作為一個顧客，我想在訂單取消時拿回我用掉的券，這樣我沒有損失。
22. 作為一個店家經營者，我想要限量券在同時湧入時不會超發，這樣我不會賠錢。
23. 作為一個店家經營者，我想要有人暴力嘗試券碼時被擋下來，這樣我的活動不會被掃碼機器人吃掉。
24. 作為一個店家經營者，我想要系統產生的券碼不易被猜到也不易被看錯，這樣客服不用處理「我打對了啊」。
25. 作為一個資料分析者，我想要每一次核銷都留下紀錄，這樣我的報表不必掃全部訂單。

## Implementation Decisions

### 模型

- `Promotion`（Spec 0002 已建立）是規則本身，不變。
- 新增 `Coupon`：指向一個 Promotion，有唯一的碼、狀態（已發放／已使用／已過期／已作廢）、
  可選的擁有者（顧客）、可選的合作夥伴（歸因對象）、有效期間。
- **共用碼**是沒有擁有者的 Coupon，多人可用，靠總量與每人次數限制控制。
- **實發券**是有擁有者的 Coupon，只有該顧客能用。
- **行銷碼**是共用碼再加上合作夥伴 —— 折價行為與公開折扣碼完全相同，唯一增量是歸因。
- 滿額折這類人人適用的活動維持「只有 Promotion、沒有 Coupon」。

### 核銷與併發

- 核銷發生在**結帳的同一個交易內**，與訂單一起成敗。這是行銷功能必須是 Core 模組的直接理由（ADR 0013）。
- 限量控制以資料庫的條件更新達成：只在剩餘量大於零時扣減，扣不到就讓該筆結帳失敗並回報明確原因。
  不採預留式（試算時就鎖券）—— 那會把購物車的複雜度提前引進來。
- 「每人限用一次」以顧客與 Promotion 的唯一約束達成。
- 試算階段**不**扣減任何額度，因此試算成功不保證結帳成功。這個落差要在 UI 上誠實呈現。

### 歸因

- 一張訂單最多只能有一個帶歸因的 Coupon。這條限制在定價引擎之外以明確的驗證擋掉，
  **不**靠 Promotion 的疊加旗標 —— 折扣能否疊加與歸因唯一性是兩件不同的事。
- 歸因只認結帳時實際輸入的碼，不認連結點擊、不種追蹤 cookie。
- 佣金不由系統計算。後台提供的是成效數字，結算靠人工。

### 發券

- 三種觸發：後台手動批次、領域事件觸發（新會員註冊）、排程觸發（生日）。
- 三個觸發點共用同一個內部發券函式。**不**先做「發券活動」這一層抽象 ——
  在只有三種觸發時那是規則引擎的規則引擎。第四種觸發出現時再抽象。
- 生日發券需要每日執行，在工作上宣告 `schedule` 即可（ADR 0016）。注意切片邊界對齊 UTC，
  「生日當天」的判斷必須由 handler 自己以店鋪時區決定。
- 實發券的通知走 Spec 0001 建立的 `notification` Provider。

### 券碼

- 共用碼由後台自訂，人可讀（例如 `SUMMER20`）。
- 實發券碼由系統產生，至少 12 字元，使用不易混淆的字母集（排除易混字元）。
- 套用券的端點加上節流，沿用登入端點既有的節流機制。
- 實發券綁定擁有者，因此猜中他人的碼也無法使用；真正的風險只在共用碼，
  而共用碼的損失上限是活動總量本身。

### 取消回沖

- 訂單取消時，用掉的 Coupon 恢復可用，總量計數回補。
- 部分退貨不在模型內（Spec 0005 同此立場）。

### 核銷紀錄與分析

- 每一次核銷寫入明細：哪張券、哪個 Promotion、哪張訂單、折抵多少、歸因給誰、何時。
- 這張明細表同時是行銷分析的事實來源 —— 報表查它，不掃訂單全表（見 Spec 0005 的 Analytics 頁）。

### 前台與後台

- 前台：購物車頁可輸入與移除折扣碼；會員中心可看自己的券清單與到期日。
- 後台：券的清單與建立、批次發券、單一活動的成效數字。

## Testing Decisions

好的測試驗的是「輸入這個碼、結帳、得到什麼結果」，不是券在資料表裡的欄位長相。
併發相關的測試必須真的併發，不能只驗單執行緒的邏輯。

兩個接縫：

1. **Command / Query Bus（integration）** — 券的建立與發放、套用成功與各種失敗原因、
   每人限用一次、有效期邊界、取消回沖、歸因寫入、核銷明細正確、
   以及**限量券的併發**：多個同時結帳只有額度內的成功，總量不超發。
   前例：`tests/integration/idempotency.test.ts`（併發語意的既有寫法）、
   `tests/integration/flow-order-outbox.test.ts`。
2. **純函式定價引擎（unit）** — 券所指向的 Promotion 與其他活動的疊加、優先序、
   歸因唯一性驗證。沿用 Spec 0002 建立的測試套件與工具。

事件觸發的發券（新會員註冊）沿用既有的事件流測試方式，
前例：`tests/integration/flow-extension-erp.test.ts` 的事件到工作的完整鏈路。
排程發券（生日）以可注入的當下時間測試，不依賴真實時鐘。

## Out of Scope

- 佣金計算與結算、付款給合作夥伴。
- 連結點擊歸因、追蹤 cookie、歸因窗口、first-click / last-click 之爭。
- 合作夥伴自己的後台（partner portal）。
- 加價購 —— 它是 Promotion 回傳「可加購清單」的延伸，排在本規格之後。
- 部分退貨時的券回沖。
- 券的轉贈、交易、二維碼／實體券。
- 多個帶歸因的碼並用。

## Further Notes

「試算不鎖券、結帳才扣」意味著在極熱門的限量活動中，顧客可能在試算看到折扣、
結帳卻失敗。這是刻意的取捨：預留式會需要券的預留生命週期、過期釋放與購物車綁定，
複雜度接近庫存預留系統。UI 必須誠實處理這個落差，而不是假裝它不存在。

加價購（門檻達成後可用特價加購某商品）在本規格之後接續：
它的門檻判斷與滿額折是同一種條件判斷，共用引擎才不會出現兩套「什麼叫滿額」的定義。
屆時定價引擎的輸出要從「只有價格調整」擴充為「價格調整 + 可加購清單」。
