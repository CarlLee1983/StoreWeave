# Spec 0002 — 定價引擎與訂單金額模型

- 狀態：ready-for-agent
- 依賴：無（與 Spec 0001 並行，在 Spec 0003 會合）
- 相關 ADR：0015（訂單金額模型）、0013（行銷是 Commerce 模組）、0006（事件版本）

## Problem Statement

這個購物站算不出折扣。訂單的總額恆等於商品小計，沒有任何地方可以表達「這張單折了多少、
為什麼折、折在哪一件商品上」。經營者想辦一場「滿一千折一百」的活動，系統沒有任何機制承接。

更麻煩的是，即使勉強加一個折扣總額欄位，第一次部分退貨就會發現算不回來：
沒有人知道那件被退的商品實際收了多少錢。

## Solution

訂單的金額模型改成「小計 + 一組具名的價格調整 = 總額」，而每一筆調整都必定分攤到具體的商品行上。
折扣的計算由一個**純函式定價引擎**負責：餵給它購物內容與情境，它回傳每一行的調整明細，
不碰資料庫、不產生副作用。

經營者可以在後台建立促銷活動，選擇規則型別（滿額折固定金額、滿額折百分比、整單百分比），
設定條件與期間，活動即時生效於所有結帳。

## User Stories

1. 作為一個店家經營者，我想要建立一個「滿一千折一百」的促銷活動，這樣我可以刺激客單價。
2. 作為一個店家經營者，我想要建立一個「滿兩千打九折」的促銷活動，這樣我有百分比型的選擇。
3. 作為一個店家經營者，我想要建立一個無門檻的整單折扣活動，這樣我可以辦全站特賣。
4. 作為一個店家經營者，我想要為每個活動設定生效與結束時間，這樣活動會自己開始與結束。
5. 作為一個店家經營者，我想要隨時停用一個進行中的活動，這樣我可以緊急喊停。
6. 作為一個店家經營者，我想要決定一個活動能不能跟其他活動疊加，這樣我可以控制折扣成本。
7. 作為一個店家經營者，我想要決定活動之間的套用順序，這樣「先打折再滿額」和「先滿額再打折」由我決定。
8. 作為一個店家經營者，我想要清楚知道運費算不算進滿額門檻，這樣我不會誤設活動。
9. 作為一個顧客，我想在結帳前看到折扣後的金額，這樣我知道實際要付多少。
10. 作為一個顧客，我想看到每一筆折扣的名稱，這樣我知道我為什麼便宜了。
11. 作為一個顧客，我想要試算時看到的金額跟實際扣款一致，這樣我不會有被騙的感覺。
12. 作為一個顧客，我想在活動剛好結束的那一刻結帳時，得到明確且一致的結果，而不是有時有折有時沒折。
13. 作為一個店家經營者，我想要每張訂單記下當時套用了哪些活動，這樣我事後查得到帳。
14. 作為一個會計，我想知道每一件商品實際收了多少錢，這樣我開得出發票。
15. 作為一個客服，我想在部分退貨時知道該退多少錢，這樣我不會退錯。
16. 作為一個 ERP 串接方，我想要訂單事件裡的金額欄位語意明確，這樣我的帳能對得起來。
17. 作為一個 ERP 串接方，我想要在金額語意改變時有一段緩衝期，這樣我來得及跟上。
18. 作為一個開發者，我想要定價邏輯是純函式，這樣我可以用幾百個案例在毫秒內驗證它。
19. 作為一個開發者，我想要新增一種折扣規則型別時不必改引擎本身，這樣擴充成本是線性的。
20. 作為一個開發者，我想要分攤的餘數有明確且穩定的規則，這樣同樣的輸入永遠得到同樣的結果。
21. 作為一個店家經營者，我想要總折扣不會超過商品小計，這樣不會出現負數訂單。
22. 作為一個資料分析者，我想要營收數字反映折扣後的實收金額，這樣報表不會虛胖。

## Implementation Decisions

### 新模組

- 新增 `packages/commerce/promotion` 模組，與 catalog / inventory / order 平起平坐（ADR 0013）。
  它擁有促銷活動的資料表，並匯出供 order 模組在同一交易內呼叫的 service。
- 定價引擎是這個模組裡的**純函式**：輸入購物內容與情境，輸出每一行的調整明細與總額。
  它不接受 `tx`、不查資料庫、不讀時鐘 —— 當下時間由呼叫端傳入。

### 定價引擎的契約

- 輸入：商品行（商品識別、單價、數量、分類/標籤）、情境物件、當下時間。
- 情境物件是**開放結構**而非固定欄位集合，之後加入新的判斷依據不算破壞性變更。
  第一版的情境包含：適用的促銷活動清單、顧客的會員等級（若已登入）。
- 情境**不含歷史消費額**。「首購優惠」「累積消費滿三次」這類規則留待後續，
  它們會讓每次結帳多一次統計查詢。
- 輸出：每一行的 Adjustment 明細、訂單層彙總、以及套用了哪些活動的紀錄。

### 規則型別

- 第一批內建三種：滿額折固定金額、滿額折百分比、整單百分比。
- 規則型別可插拔：引擎依型別分派，新增型別不改引擎的核心流程。
- 每個活動有優先序與「可否疊加」旗標。引擎依優先序依序套用；遇到不可疊加的活動被套用後，
  後續不可疊加的活動不再套用。
- 「滿額」的門檻一律以**商品小計**判斷，不含運費、不含稅。這是全系統唯一的定義。

### 分攤

- 訂單層的 Adjustment 按各行金額比例攤回每一行，餘數（因整數分而產生）給金額最高的那一行；
  金額相同時給排序在前的那一行。規則必須是決定性的。
- 分攤後每一行的實收金額不得為負；引擎保證總折扣不超過商品小計。

### 金額欄位與事件

- `order_orders` 新增 `discount_cents`、`shipping_cents`、`tax_cents`；`total_cents` 從
  「等於小計」變成計算結果。`order_lines` 新增 line 層級的折扣欄位。
- 運費與稅在本規格不實作，欄位恆為 0。刻意一次補齊，避免第二次破壞性事件變更（ADR 0015）。
- 訂單新增一組「本張訂單套用了哪些活動、各折多少」的明細，它同時是行銷分析的事實來源之一。
- `commerce.order.placed` 與 `commerce.order.paid` 發新版本，舊版依 ADR 0006 續發至少一個
  minor 週期。已知下游：demo-erp 的 transform、Admin 訂單頁、`salesSummary`。

### 試算入口

- 新增一支無副作用的 Query 供前台即時試算。它與結帳走**同一個定價引擎**，
  差別只在結帳會把結果凍結進訂單。試算不鎖定任何額度。

### 後台

- Admin 新增「促銷活動」頁：清單、建立、編輯、停用。
- 每種規則型別有專屬的表單元件，型別清單在 Admin 端編譯期已知。
  不做 schema 驅動的動態表單 —— 折扣設定需要大量客製 UI（商品選擇器、期間、預覽試算）。

## Testing Decisions

好的測試在這裡特別容易寫對：定價引擎是純函式，測試就是「給定輸入，斷言輸出」，
不需要資料庫、不需要 mock、不需要時間控制（時間是參數）。不要測引擎內部怎麼分派規則型別。

兩個接縫：

1. **純函式定價引擎（unit）** — 這是本規格的主要測試面，也是這個 repo 第一個領域邏輯的
   套件級單元測試套件。必須涵蓋：三種規則各自的邊界（剛好達門檻、差一分、超過很多）、
   優先序、疊加與不可疊加的組合、分攤的餘數與決定性、折扣不超過小計、活動期間的邊界時刻。
   組合數會很大，這正是選純函式的原因。
   前例：`packages/platform/command-bus/test/hash.test.ts` 這類無相依的純函式測試。
2. **Command / Query Bus（integration）** — 促銷活動的 CRUD、下單時折扣真的落進訂單與 line、
   新舊事件版本同時發出、稽核紀錄。前例：`tests/integration/flow-order-outbox.test.ts`。

必要的迴歸測試：`salesSummary` 在營收語意改變後的行為。它與 `SalesSummarySection`
目前**完全沒有測試覆蓋**，遷移前要先補上現況的測試，否則無法證明沒改壞。

Admin 促銷活動頁沿用既有的 jsdom project，前例 `apps/admin/src/pages/DlqPage.test.tsx`。

## Out of Scope

- 優惠券與任何需要「輸入一組碼」的東西 —— 屬於 Spec 0004。本規格的活動是人人適用的。
- 購物金折抵 —— 屬於 Spec 0005。引擎的輸出結構要能容納它，但本規格不實作。
- 加價購 —— 引擎目前只回傳價格調整，不回傳「可加購清單」。
- 運費與稅的實際計算。欄位存在但恆為 0。
- 指定商品折扣、買 X 送 Y、第二件半價等其他規則型別。
- 歷史消費額類的規則。
- 部分退貨。分攤的存在是為了讓它未來可行，但本規格不實作它。

## Further Notes

本規格與 Spec 0001 沒有相依，可以並行進行 —— 這是「定價引擎是純函式」的意外紅利：
它不需要顧客、不需要購物車、不需要 HTTP 就能完成並驗證。
兩條線在 Spec 0003（購物車結帳套用折扣）會合。

事件版本升級是本規格風險最高的部分，因為下游是已經在運作的 Extension 與 Admin。
建議的順序是：先補 `salesSummary` 的現況測試 → 加欄位（恆為 0，行為不變）→
發新事件版本（與舊版並行）→ 接上定價引擎 → 下游遷移 → 舊版下線。
