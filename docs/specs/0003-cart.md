# Spec 0003 — 購物車

- 狀態：ready-for-agent
- 依賴：Spec 0001（顧客身分）、Spec 0002（定價引擎）
- 相關 ADR：0009（含 2026-08-22 補充：Cart 不預留庫存）、0015（訂單金額模型）

## Problem Statement

前台一次只能買一件商品。商品頁按下購買就直接建立訂單並立刻請款，沒有中間狀態。
顧客不能湊單、不能比較、不能反悔；而經營者剛做好的「滿一千折一百」活動，
在一次只能買一件的前台等於無效。

同時，結帳的冪等保護是壞的 —— 每次請求都用新產生的識別碼，重複送出表單會建出多筆訂單。

## Solution

引入購物車。顧客可以陸續加入多件商品、調整數量、移除，隨時看到套用折扣後的預估金額。
訪客也能有購物車；登入後它併入會員的購物車，不會白逛一場。

購物車不預留庫存 —— 放進購物車不保證買得到，可售量在結帳當下才驗證。
結帳時購物車的識別碼成為冪等鍵，重複送出不會建出第二張訂單。

## User Stories

1. 作為一個訪客，我想要把商品加進購物車，這樣我可以繼續逛而不必馬上決定。
2. 作為一個訪客，我想要在關掉瀏覽器再回來時購物車還在，這樣我不用重加一次。
3. 作為一個顧客，我想要調整購物車裡某件商品的數量，這樣我不用移除再重加。
4. 作為一個顧客，我想要從購物車移除一件商品，這樣我可以改變主意。
5. 作為一個顧客，我想要清空整個購物車，這樣我可以重新開始。
6. 作為一個顧客，我想要看到購物車的商品小計，這樣我知道目前買了多少。
7. 作為一個顧客，我想要看到目前適用的折扣與折扣後金額，這樣我知道還差多少可以達到門檻。
8. 作為一個顧客，我想要在快達到滿額門檻時被提示還差多少，這樣我有動機多買一點。
9. 作為一個訪客，我想在登入後保留我逛街時放進購物車的東西，這樣登入不會懲罰我。
10. 作為一個在兩個裝置都放了同一件商品的顧客，我想要合併後的數量符合我的意圖，而不是被加倍。
11. 作為一個顧客，我想在購物車裡的商品下架時被清楚告知，而不是結帳時才失敗。
12. 作為一個顧客，我想在商品漲價時看到的是最新價格，這樣結帳金額不會突然變動。
13. 作為一個顧客，我想在結帳時才被要求登入，這樣我可以先確認要買什麼。
14. 作為一個顧客，我想要用購物車一次下單多件商品，這樣我只需要付一次款。
15. 作為一個顧客，我想在網路不穩重複送出結帳時，只產生一張訂單，這樣我不會被重複扣款。
16. 作為一個顧客，我想在結帳失敗（庫存不足）時知道是哪一件商品出問題，這樣我可以調整後重試。
17. 作為一個顧客，我想在結帳成功後購物車被清空，這樣我不會誤以為東西還沒買。
18. 作為一個店家經營者，我想要放進購物車不佔用庫存，這樣熱門商品不會被殭屍購物車鎖死。
19. 作為一個店家經營者，我想要長期沒動的訪客購物車被清掉，這樣資料表不會無限膨脹。
20. 作為一個店家經營者，我想要會員的購物車長期保留，這樣未來我可以做棄單再行銷。
21. 作為一個開發者，我想要購物車試算與結帳算出完全一致的金額，這樣不會有客訴。

## Implementation Decisions

### 歸屬與識別

- 購物車屬於 `packages/commerce` 的一個模組（可與 customer 或 order 同層，實作時決定）。
- 訪客購物車以一個匿名 token 綁定，token 存在 cookie 裡；這是前台第一個訪客識別機制。
- 會員購物車以顧客識別綁定。一個顧客最多一個有效購物車。

### 合併

- 訪客登入時，其購物車併入該顧客的購物車。
- 同一件商品同時存在於兩邊時**取較大數量**，不是相加。理由：使用者在兩個裝置各放一件時，
  意圖幾乎總是「我要一件」；相加會製造客訴。
- 合併時已下架的商品靜默移除，並在合併完成後向使用者提示發生了什麼。

### 價格

- 購物車**不凍結價格**。顯示的金額永遠是當下重新試算的結果。
- 試算走 Spec 0002 的同一個定價引擎，經無副作用的 Query 入口。不鎖定任何額度。
- 價格凍結只發生在購物車轉成訂單的那一刻。

### 庫存

- 購物車**不預留庫存**（ADR 0009 補充）。可售量的驗證與失敗發生在結帳當下。
- 既有的 15 分鐘預留機制維持不變，起點仍是建立訂單。

### 結帳

- 結帳將購物車轉成訂單：帶入所有商品行、由 Actor 決定下單者、當場執行定價引擎並凍結金額。
- **購物車識別碼成為結帳的 idempotency key**，取代目前每次現產的隨機值。
  重複送出同一個購物車的結帳，得到同一張訂單。
- 結帳成功後購物車被清空（或標記為已結帳，實作時決定，但顧客看到的是空車）。
- 未登入呼叫結帳一律拒絕並引導登入（Spec 0001 已定結帳必須是會員）。

### 生命週期

- 訪客購物車 30 天未更新即過期清理；會員購物車永久保留。
  會員購物車的保留是有用途的：棄單再行銷需要「最後更新於 N 天前」這個查詢。
- 清理由背景工作執行。平台沒有排程器，週期性由模組在工作上宣告 `schedule` 取得，
  機制與取捨見 ADR 0016（時間切片，不是自我續排的鏈）。

### 前台

- 商品頁的「立即購買」改為「加入購物車」，新增購物車頁與結帳流程。
- 前台由 Theme 負責呈現，Theme 契約需要新增購物車與結帳的 render 出口。

## Testing Decisions

好的測試驗的是外部可觀察的結果：購物車的內容、試算金額、結帳後的訂單與庫存變化。
不要斷言購物車在資料庫裡怎麼存、合併演算法內部怎麼比較。

兩個接縫：

1. **Command / Query Bus（integration）** — 加入/調整/移除/清空、試算金額與定價引擎一致、
   合併規則（取較大值、下架商品移除）、結帳轉單、結帳的冪等（同一購物車送兩次得到一張訂單）、
   庫存不足時的失敗與訊息、結帳後購物車清空、過期清理。
   前例：`tests/integration/flow-catalog-inventory.test.ts`、`tests/integration/idempotency.test.ts`。
2. **HTTP（integration）** — 訪客 token 的 cookie 簽發與辨識、登入時的合併時機、
   未登入結帳被拒。前例：`tests/integration/auth-http.test.ts`。

特別值得寫的測試：**試算與結帳金額一致**。用同一組購物內容分別走試算 Query 與結帳，
斷言兩者的 Adjustment 明細完全相同。這條測試是「同一套定價引擎兩個入口」這個決策的守門員。

## Out of Scope

- 優惠券與行銷碼的輸入 —— 屬於 Spec 0004。購物車的結構要能容納「本次使用的券」，但本規格不實作。
- 購物金折抵 —— 屬於 Spec 0005。
- 加價購。
- 棄單再行銷（提醒信、恢復連結）。本規格只保證資料留著讓它未來可行。
- 購物車層級的庫存預留。
- 願望清單、稍後再買、多個購物車。
- 運費試算。

## Further Notes

`POST /checkout` 目前的 idempotency key 是每次請求現產的隨機值，等於沒有冪等保護。
本規格是修復它的正確位置 —— 購物車識別碼是那個 key 天然的來源。在此之前這個缺陷仍然存在。

Theme 契約新增 render 出口是一個公開契約變更。目前只有一個預設 Theme，成本很低，
但這件事應該一次做對：購物車與結帳是任何購物型 Theme 都必須實作的，不是選配。
