# Spec 0005 — 購物金、會員等級與行銷分析

- 狀態：ready-for-agent
- 依賴：Spec 0001（顧客身分）、Spec 0002（定價引擎）、Spec 0003（購物車）、Spec 0004（核銷紀錄）
- 相關 ADR：0014（顧客身分）、0015（訂單金額模型）、0013（行銷是 Commerce 模組）

## Problem Statement

顧客買完就走，沒有任何留下來的理由。經營者辦了活動、發了券，卻看不出哪一檔有效 ——
現有的營收摘要只有訂單數與總額，而且藏在「系統健康」頁底下，掃的是訂單全表。

同時，「點數」這個詞在需求裡同時指兩件事：決定會員等級的累積值，
以及可以折抵金額的準貨幣。它們的累積條件不同、能力不同，混為一談會做錯。

## Solution

兩種明確區分的累積：**等級積分**決定會員等級但不能折抵金額，滾動十二個月計算因此會降級；
**購物金**是可折抵訂單金額的準貨幣，以分批帳本記錄，每一批有自己的生效日與到期日。

行銷分析獨立成一個頁面，第一批只回答一個問題：每一檔活動帶來多少核銷、折抵多少、多少訂單與營收。
它查的是 Spec 0004 建立的核銷明細，不掃訂單全表。

## User Stories

1. 作為一個顧客，我想在付款完成後獲得購物金，這樣我有理由再回來買。
2. 作為一個顧客，我想清楚知道我有多少購物金可用，這樣我可以規劃下次購物。
3. 作為一個顧客，我想知道我的購物金什麼時候到期，這樣我不會白白浪費。
4. 作為一個顧客，我想知道我的購物金什麼時候才能開始使用，這樣我不會誤會系統壞了。
5. 作為一個顧客，我想看到每一筆購物金的來源與去向，這樣我對餘額有信心。
6. 作為一個顧客，我想在結帳時選擇要折抵多少購物金，這樣我可以自己決定要不要用掉。
7. 作為一個顧客，我想要折抵的金額不超過商品小計，這樣不會出現我還要倒拿錢的怪事。
8. 作為一個顧客，我想在訂單取消時拿回我折抵掉的購物金，這樣我沒有損失。
9. 作為一個顧客，我想在訂單取消時被扣回那張單累積的購物金，並且理解為什麼。
10. 作為一個顧客，我想要即將到期的購物金會通知我，這樣我有機會用掉。
11. 作為一個顧客，我想知道我目前的會員等級，這樣我知道我享有什麼待遇。
12. 作為一個顧客，我想知道升到下一級還差多少，這樣我有努力的方向。
13. 作為一個顧客，我想知道我的等級是怎麼算出來的以及何時會重新計算，這樣降級時我不會覺得被欺騙。
14. 作為一個高等級會員，我想要享有更高的購物金累積倍率，這樣等級有實質意義。
15. 作為一個高等級會員，我想要有些促銷活動只有我適用，這樣等級有排他的價值。
16. 作為一個店家經營者，我想要設定每一級的門檻與名稱，這樣等級制度符合我的經營策略。
17. 作為一個店家經營者，我想要設定購物金的累積比例與生效天數，這樣我可以控制成本與套利風險。
18. 作為一個店家經營者，我想要手動調整某個會員的購物金，這樣我可以處理客訴與補償。
19. 作為一個店家經營者，我想要每一筆手動調整都留下操作者與原因，這樣事後查得到帳。
20. 作為一個店家經營者，我想要看到目前流通在外的購物金總額，這樣我知道我背了多少負債。
21. 作為一個店家經營者，我想要看到每一檔活動的核銷次數與折抵總額，這樣我知道錢花在哪。
22. 作為一個店家經營者，我想要看到每一檔活動帶來的訂單數與營收，這樣我可以判斷投報率。
23. 作為一個店家經營者，我想要看到每一個合作夥伴的行銷碼帶來多少業績，這樣我可以人工計算佣金。
24. 作為一個店家經營者，我想要行銷分析有自己的頁面，而不是藏在系統健康底下，這樣我找得到它。
25. 作為一個店家經營者，我想要營收數字反映折扣後的實收金額，這樣我不會高估業績。
26. 作為一個店家經營者，我想要報表在資料量變大時仍然打得開，這樣它是可用的工具而不是裝飾。
27. 作為一個開發者，我想要餘額是帳本的推導值而不是一個可以被寫壞的欄位，這樣對帳永遠成立。

## Implementation Decisions

### 兩種累積，兩本帳

- **等級積分**與**購物金**是兩個不同的東西，在程式碼、資料庫、UI 與文件中都不共用名稱。
  任何地方都不單獨出現「點數」二字（`CONTEXT.md` 已定）。
- 兩者都以 **append-only 的分批帳本**記錄，餘額與等級都是帳本的推導值，不是欄位。
  這個結構從第一天就採用：從餘額欄位改成帳本是資料遷移地獄，反過來很容易。
- 每一筆分錄記錄：金額／積分、來源（哪張訂單、哪次手動調整）、生效時間、到期時間、操作者。

### 購物金

- **入帳時機**：付款完成時入帳，但帶一個生效日（付款後 N 天，N 由後台設定、預設 7）。
  給太早會被套利（下單拿金、取消訂單、購物金留著）；生效日讓取消回沖只是扣掉一筆尚未生效的分錄，
  不會出現餘額變負數。
- **累積比例**由後台設定，並乘上會員等級的倍率。
- **折抵**是定價引擎最後套用的一筆 Adjustment，只作用在商品小計上 —— 不折運費、不折稅。
- 折抵額由顧客在結帳時決定，上限是可用餘額與商品小計兩者的較小值。
- **到期**：每一批有自己的到期日，先到期的先使用。到期不需要排程改狀態 ——
  可用餘額的計算本身就排除已過期的批次；到期通知才需要排程。
- **取消回沖**：訂單取消時，折抵掉的購物金以反向分錄回沖、該單累積的購物金以反向分錄扣回。
  不是把餘額加減回去 —— 帳本永遠只增不改。
- 部分退貨不在模型內。

### 等級積分與會員等級

- 等級積分以**滾動十二個月**計算，因此會降級。只升不降的等級制在幾年後會讓所有人都是最高等級。
- 等級由積分帳本在有效期間內的總和推導。等級的重新計算需要定期執行，
  在工作上宣告 `schedule` 即可（ADR 0016）。
- 等級的能力只有兩項：影響適用哪些 Promotion、影響購物金累積倍率。
  **等級不是獨立的折扣系統** —— 它只是定價引擎情境物件裡的一個輸入變數，
  否則會出現兩套折扣邏輯。
- 等級門檻與名稱由後台設定。

### 手動調整

- 後台可以手動增減某個會員的購物金與等級積分，每一筆都是帶操作者與原因的帳本分錄，
  並寫入稽核紀錄。這是客服補償的正式管道。

### 行銷分析

- 新增獨立的 Analytics 頁，並把現有藏在系統健康頁裡的營收摘要移過來。
- 第一批指標只有一組：**每一個 Promotion 的核銷次數、折抵總額、帶來的訂單數與營收**，
  資料來源是 Spec 0004 的核銷明細表，不掃訂單全表。行銷碼的成效是同一份資料按合作夥伴分組。
- 另外提供「流通在外的購物金總額」，由帳本聚合。
- **不建 projection 或 read model**。核銷明細本身就是事實表，而且天生比訂單表小得多。
  跨模組的指標（用券客的回購率、棄單率）需要真正的聚合基礎建設，不在本規格。
- 既有的營收摘要在 Spec 0002 之後語意已變（折扣後實收），本規格接手它的呈現。

## Testing Decisions

好的測試在這裡要特別小心一件事：**不要斷言餘額欄位**，因為沒有餘額欄位。
測的是「做了這些事之後，可用餘額推導出來是多少」。時間相關的行為以可注入的當下時間測試，
不依賴真實時鐘，也不用 sleep。

三個接縫：

1. **純函式（unit）** — 餘額推導（含未生效、已過期、先進先出的使用順序）、
   等級由滾動期間積分推導、購物金折抵的上限計算。這些都是純計算，
   應該與 Spec 0002 的定價引擎測試套件並列，用大量案例覆蓋時間邊界。
2. **Command / Query Bus（integration）** — 付款後入帳、生效日、結帳折抵、取消回沖、
   手動調整與稽核紀錄、等級重算工作、行銷分析查詢的數字正確。
   前例：`tests/integration/flow-order-outbox.test.ts`。
3. **Admin 元件（jsdom）** — Analytics 頁。前例：`apps/admin/src/pages/DlqPage.test.tsx`。

必須先補的迴歸測試：現有的營收摘要查詢與其 UI 區塊目前**完全沒有測試覆蓋**。
在把它搬到 Analytics 頁之前先補上現況測試，否則無法證明搬家沒改壞（Spec 0002 已提出同一件事，
以先發生者為準）。

特別值得寫的測試：一連串入帳、折抵、取消、到期之後，帳本的總和與可用餘額仍然一致。
這條測試是「餘額是推導值」這個決策的守門員。

## Out of Scope

- 部分退貨時的購物金與等級積分回沖。
- 購物金的儲值、轉贈、提領、跨帳號轉移。
- 等級的手動指定（VIP 白名單）與等級保護期。
- 回購率、客戶終身價值、棄單率、漏斗分析 —— 需要跨模組聚合基礎建設。
- projection / read model / 事件封存 / 資料倉儲。
- 報表匯出（CSV／排程寄送）。
- 購物金的財務會計整合（真正的負債科目入帳）。本規格只提供流通總額這個數字。
- 加價購。

## Further Notes

購物金一旦能折抵金額，它就是一本負債帳。本規格提供的是營運層面的正確性
（帳本不會被寫壞、餘額永遠可推導、取消一定回沖），不是財務會計層面的整合。
若之後要與會計系統對接，帳本結構已經是對的形狀。

「先到期的先使用」這條規則對顧客有利，也讓到期通知有意義。它讓餘額計算不能是簡單的加總，
而是要按批次排序後才知道用掉哪些 —— 這是選擇分批帳本的主要成本，也是它唯一的複雜之處。

等級降級會產生客訴。UI 必須主動說明滾動期間的計算方式與下次重算時間，
而不是等顧客發現等級掉了才解釋。
